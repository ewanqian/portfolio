01 / START

先不要问“我该学哪个软件”

实时视听创作很容易从工具开始：先打开一个软件，再寻找插件、参数和效果。这样当然可以工作，但也很容易让创作者陷入一个循环——功能越来越多，作品却越来越难解释。

这场工作坊把顺序反过来。我们先确定一个动作，再决定这个动作和系统之间的关系。

一个动作 ↓ 一套规则 / Mapping ↓ 声音 + 视觉 + 系统状态 ↓ 观众看到结果 ↓ 表演者根据结果再次判断

技术不是起点。
真正的起点是：我希望这个系统怎样回应我？

第一步可以简单到只有一个键、一次触摸或一次鼠标动作。问题不是“它能触发多少效果”，而是这个动作能不能形成清楚、可理解、可以继续发展的结果。

02 / MAPPING

什么是“音画同源”？

这里的“音画同源”不是一个固定的艺术史流派名称，而是我们在工作坊里使用的工作概念：声音和视觉不只是最后被摆在一起，而是尽可能从同一个动作、状态、参数或规则中共同产生。

反应式可视化

声音先出现，再分析音量、频率或节拍，让画面跟着变化。声音是原因，视觉是反应。

同源控制

一个输入先进入控制系统，再分别影响声音与视觉。两者是同一套决定的不同结果。

INPUT / GESTURE ↓ MAPPING / RULE ↙ ↘ SOUND VISUAL ↘ ↙ SHARED STATE

最简单的版本当然可以是“按一下，同时响一下、闪一下”。但如果结果永远只由当前这一下决定，它很快就会被观众看穿。真正有意思的部分，是让同一个输入进入不同状态、不同时间位置和不同历史之后，拥有不同意义。

03 / FAILURE

先玩两个故意做坏的版本

很多实时 Demo 会失败在两个相反方向：一种太薄，另一种太满。它们看上去完全不同，根本问题却一样——只有事件，没有结构。

Bad Demo A · Too ThinTrigger Baseline

每次输入都得到完全相同的声音和视觉。请连续玩 20–30 秒，不要急着判断。

回来以后问自己：第 1 次和第 20 次触发，有没有因为“前面发生过什么”而产生不同意义？
试玩：太薄的系统 ↗
Bad Demo B · Too FullOverload Trap

连续按 Space 或点击 10–15 秒。每次输入只会继续增加层，鼠标还直接拖着视觉中心走。

回来以后问自己：能不能只减少一点？能不能等待？能不能在 8 bars 后释放？还是只能全部 Reset？
试玩：过载陷阱 ↗

两个坏例子的共同点：一个什么都留不住，一个什么都舍不得删。它们都缺少 State、时间结构、退出方式和反馈回路。

更多效果，不等于更多控制。

04 / CONTROL

从 Trigger 到 State，再到 Feedback

要让一个实时网页从“会触发”走向“可以演”，至少要多出三件事：系统知道自己现在在哪里；输入会改变这个状态；表演者能看到结果并继续判断。

现在系统是什么状态 + 人刚刚做了什么 + 现场已经发生过什么 ↓ 系统进入下一个状态 ↓ 声音 / 视觉产生结果 ↓ 人听见、看见结果 ↓ 再决定下一步
Good Step 01State Instrument

同一个 Space，在 QUIET 与 ACTIVE 中得到不同结果。先在 QUIET 触发几次，再切 ACTIVE，再触发同一个输入。

注意：按钮没有增加，但“当前状态”开始参与结果。
试玩 State Instrument ↗
Good Step 02Safe Loop

启动以后先什么都不做 8 秒。系统自己维持 BPM 和基本连续性；然后只用 ADD、REMOVE、HOLD、RELEASE 去改变结构。

注意：你不再手工制造每个 beat，而是在提出“增加、等待、减少、释放”的意图。
试玩 Safe Loop ↗

人和系统各自负责什么？

系统负责安全

BPM、节拍边界、音量限制、最大声部、最大视觉密度、自动衰减、Reset / Panic。

人负责判断

什么时候进入、什么时候继续等待、什么时候增加、什么时候减少、什么时候释放、什么时候结束。

这样做不是让机器替人表演，而是把最容易出错、最需要精确计算的部分交给系统，把最有创作价值的结构判断留给人。

05 / STRUCTURE

为什么音乐、视觉和灯光都需要结构？

一场演出通常不会把所有能量从第一秒开到最后一秒。音乐会有铺垫、推进、高潮、间隔和收束；灯光会隐藏、聚焦、打开、熄灭；视觉也需要建立、累积、转化和离开。

这些结构有效，不是因为存在唯一公式，而是因为它们让观众能够感受到变化的方向。

Micro / Event

一个声音、一次闪烁、一次敲击。很短。

Meso / Phrase & Section

几个事件形成一段关系，例如推进、等待与释放。

Macro / Show

整场演出的能量曲线、段落次序、高潮位置和结束方式。

Shared State

音乐、视觉、灯光可以用不同速度变化，但共同理解“现在处于什么阶段”。

STATE = PRE-RELEASE / 还不能释放 音乐：减少完整鼓组，保留紧张感 视觉：减少新对象，让已有结构继续积累 灯光：保持狭窄，不完全打开空间

三种媒介没有复制彼此，却在解释同一个状态。这是“同源”比“每拍同步”更重要的一层。

一个最小的五段演出剧本

01 / OPEN铺垫少、慢、留白。先让观众理解空间和基本材料。
02 / BUILD推进增加重复、方向和密度，但先不把所有东西放出来。
03 / PEAK主段最明确的身体能量和视觉层级。高能，但仍可控。
04 / BRIDGE桥段抽离主要脉冲，留下尾音、空间、记忆或重新组合。
05 / RETURN收束回到更少的材料，决定结束、重启，或召回旧元素。

控制不是把更多参数握在手里。
控制是决定什么在什么时候发生。

06 / PLAY ROUTE

课堂试玩路线：按这个顺序就够了

下面不是软件清单，而是一条从“坏”到“可演”的比较路线。每次试玩只需要几十秒到两分钟。重要的是每次回来都回答一个问题。

Trigger Baseline：先感受“薄”

连续触发 20–30 秒。不要加新功能。

问题：如果我停手，系统还剩下什么？第 20 次按键和第 1 次有什么结构差异？
打开 Demo 00 ↗
Overload Trap：再感受“满”

快速触发 10–15 秒，让画面和声音堆起来，然后停手。

问题：我能不能只退一步？能不能降低能量而不是全部清空？
打开 Bad Demo B ↗
State Instrument：同一个输入，不同意义

在 QUIET 和 ACTIVE 中分别用同一个 Space 触发。

问题：我们增加的是按钮，还是增加了系统对“现在在哪里”的理解？
打开 Demo 01 ↗
Safe Loop：把节拍和安全交给系统

开始后先不动 8 秒，再依次尝试 ADD → HOLD → REMOVE → RELEASE。

问题：为什么停手仍然成立？为什么输入可以早一点或晚一点，但结构仍然没有马上坏掉？
打开 Demo 02 ↗
Golden Mini：先看一场，再接管一场

第一遍只听 AUTO，大约 62 秒，观察 OPEN → BUILD → PEAK → BREAK → RETURN。第二遍切 PERFORM，只使用少量结构动作。

问题：如果不看 HUD，只听声音和看画面，段落是否仍然能被感受到？
打开 Golden Mini ↗
个人材料：让系统长出身份

最后再玩“叮咚鸡 / 大狗叫”键盘版本。这里重点不是完整长时演出，而是理解自己的语音、图片和样本为什么会立刻改变一件数字乐器的性格。

问题：如果把这些材料换成你自己的声音、照片或已有作品，会发生什么？

08 / BUILD

你自己的版本，先只做四件事

进入制作以后，不要马上给自己加 26 个键。先把一个很小的系统做深。

1 · INPUT
选一个输入：一个键、一个按钮、一次触摸或一种手势。
2 · STATE
先做两个明显不同的状态，例如 QUIET / ACTIVE，或 OPEN / BUILD。
3 · CONTROL
至少有一种“回来”的动作：REMOVE、RELEASE、CLEAR 或 RESET。不要只有 ADD。
4 · MATERIAL
换成自己的声音、图像、文字或视觉结构，让系统获得身份。

如果时间够，再加 BPM / quantization。它不是为了显得专业，而是为了让不精准的输入仍能落在可靠的时间边界上。

一个最小制作模板

INPUT ↓ MAPPING ↓ STATE ↓ AUDIO + VISUAL ↓ FEEDBACK ↓ NEXT DECISION 系统保护：BPM / MAX DENSITY / GAIN / RESET 人来决定：ENTER / ADD / HOLD / REMOVE / RELEASE
09 / TEST

怎么判断它是不是开始“成立”了？

功能完成不等于作品完成。最有效的测试往往不是再写代码，而是把控制权交给别人。

30 秒无输入测试

你停手以后，系统是不是马上死掉？还是仍然有一个可以被观看的状态？

返回测试

已经很满时，能不能在有限时间内主动回到更空的状态？

盲测

作者不解释，让另一个人玩。观察他第一步做什么，而不是告诉他正确答案。

观众测试

只录 Screen + Sound，不拍键盘、不解释操作。别人看到的是“演出”还是“测试网页”？

可以反复问四句话：
现在是什么状态？
我这个动作改变了什么？
我停手以后会发生什么？
我怎么把它收回来？

最终目标不是让每个人变成程序员或音乐家。
而是开始拥有一套属于自己的实时创作与判断方法。
