工作坊参加者的背景跨度很大：有人来自数字媒体艺术、舞台设计和灯光装置，有人做音乐、Unity、VR，也有人只是希望第一次理解演出背后的工作方式。这样的背景差异反而暴露出一个重要问题：当课程只展示工具或案例时，熟悉生产流程的人可以自行补全缺失的环节，初学者却常常不知道第一步应该做什么。本册因此把“共同语言”和“最小流程”放在工具之前。

本册中的专业术语和工作文件，参考了戏剧与现场娱乐行业常见的设计流程。Yale Undergraduate Production 对 scenic designer 的要求包含 ground plan、section、elevation 等图纸；Vectorworks Spotlight 将 previsualization 定义为在真实场地之外预先检查灯光、视频和舞台效果的生产环节；QLab 则以 cue、cue list 和 cue sequence 把现场事件组织为可执行的时间结构。[1][2][3] 这些材料不会被照搬成“行业标准答案”，而是用于校准本课程的最小工作模型。

# 导论　为什么先做预演

很多视觉创作者第一次进入演出项目时，会把注意力集中在“屏幕里要做什么”。这是自然的，因为屏幕内容最接近自己的技能，也最容易在电脑上独立完成。然而真实场地不会只保留一块屏幕：屏幕有尺寸和角度，观众有观看位置，灯光会改变空间，演员和装置会遮挡内容，音乐会迫使画面在某个时间点推进或停下。一个在笔记本上成立的画面，到了现场可能只是整个关系中的一小部分。

我早期做这类尝试时，习惯用 Unity 或 Blender 建一个完整工程，再把 Render Texture、视频、灯光和镜头都塞进去。理论上这很完整，实际却经常出现另一个问题：为了看一个非常简单的空间关系，需要先解决软件、材质、实时性能和文件管理。机器一边跑场景，一边跑内容，工程越来越重，而真正需要讨论的问题——这个屏幕要不要晚一点亮、这个主体是否挡住视线、两个屏幕是否应该同时出现——反而被埋在技术细节里。

后来我开始把预演理解为一种“讨论工具”，而不是最终效果的廉价替代。预演不必把所有东西都做得真实，它首先要让项目中的人看到同一个问题。专业娱乐设计软件也遵循相近逻辑：Vectorworks Spotlight 的 Showcase 用于在真实 load-in 之前检查灯光、视频和舞台效果，支持在场地之外测试 cue、视线和设备关系。[2] 预演真正节省的不是渲染时间，而是错误被发现得更早。

这也是本册的基本立场。我们不追求“先把舞台做得像”，而追求“先把问题做得看得见”。只要一个草稿足以暴露比例、时间和媒介关系，它就已经完成了第一阶段的任务。接下来再决定哪些部分值得进入 Blender、Unreal、TouchDesigner、Arena、灯光控台或真实搭建。

> **作者札记｜工作坊里最容易跑偏的时刻**
>
> 现场常常会因为某个工具突然跑通而兴奋：网页成功抓到一个窗口、曲面屏终于对齐、反射看起来更真实。这些时刻很有趣，但也很危险。因为一旦大家开始围着“效果终于像了”打转，课程很容易忘记最初要解决的问题。
>
> 我自己犯过很多次这种错误：把大量时间花在屏幕、材质或实时效果上，最后发现创意本身并没有因此变得更清楚。所以后来我更愿意问一句：这次模拟到底要帮助我们做什么决定？

# 第一章　从场地开始：空间草稿与内容草稿

## 1.1 场地资料不是背景，而是约束

一个项目真正开始时，最可靠的信息往往不是“风格参考”，而是场地资料：屏幕尺寸、吊点、舞台深度、观众方向、进出场位置、设备数量、搭建时间。设计会不断变化，这些物理条件却通常很难在最后一刻改变。Yale 的 scenic design 指南要求设计师用 ground plan、section 和 elevation 把固定与移动的舞台元素说明清楚，并在早期就和导演、技术团队持续修订。[1] 这类文件之所以长期存在，是因为它们把“我脑子里大概是这样”变成了别人可以核对的空间关系。

对一个轻量预演来说，我们不需要一开始达到专业施工图的精度，但必须建立最低限度的共同坐标：观众从哪里看，主屏在哪里，人物或装置大概多高，哪些东西会互相遮挡。只要这几个关系不清楚，后面所有内容设计都可能建立在错误的空间假设上。

## 1.2 两种草稿：空间与内容

在工作坊里，我把草稿分成两类。第一类是空间草稿，用来处理比例、朝向、遮挡、视线和位置；第二类是内容草稿，用来处理视觉材料、音乐、灯光、节奏、情绪和版本变化。它们最终会合在一起，但不应该从第一分钟就锁死。

这个区分看似简单，却能显著降低项目的混乱程度。空间草稿的变化频率通常低于内容草稿：场地宽度不会因为你换了一套视觉就自动变大，屏幕的实际尺寸也不会因为某个镜头看起来更漂亮就改变。反过来，内容应该允许快速做很多版。如果把内容和空间从一开始就绑在一个沉重工程里，每一次改动都会牵一发动全身，团队很快就会害怕修改。

## 1.3 Gray Box 的价值

Gray Box 不是“还没做完的场景”，而是一种刻意降低信息量的工作状态。地面、屏幕、相机、一个人物或装置占位体，加上最基本的光源，已经足够回答很多重要问题。复杂材质、反射、烟雾和粒子在这个阶段往往只会提高判断成本。

我在课程里常常会给学员一个场地查看器，让他们先把屏幕四个角、折屏关系和基本观看方向对齐，再把自己的网页或视频作为 source 放进去。这个过程最有价值的地方不是“用网页替代了专业软件”，而是十几分钟内就能得到一个可共享的空间草稿。别人不需要安装你的 Blender 工程，也不需要懂你的节点结构，就能直接指出：这个屏幕太高、这个主体太靠后、顶部屏幕的进入时机不对。

> **执行提示｜场地资料不完整时怎么做**
>
> 真实项目里经常拿不到完整 CAD。可以先按信息可靠度分层：尺寸与屏幕规格优先使用场地方或供应商资料；缺失部分用现场照片、公开视频和已知物体比例做估算；无法确认的地方明确标记为“待核实”。
>
> 最危险的不是近似，而是把近似当成精确数据继续往下传。

# 第二章　从屏幕走到舞台：建立共同语言

## 2.1 设计不是单人软件操作

真正的演出生产从来不只是某个人把一段视觉做完。导演、舞美、灯光、声音、媒体、舞台管理与技术执行各自关心不同的问题。Carnegie Mellon 的 scenic design 训练把 research、script analysis、groundplan、composition、drafting、model making 与 collaborative skills 放在同一个学习体系中，原因就在这里：设计的专业性不仅体现在图像质量，也体现在一个想法能否被团队理解并落实。[4]

对于短期工作坊，没有必要复制完整的专业训练，但必须让参与者尽早接触几种跨工种文件。它们的价值不是形式感，而是把口头描述变成可以校对的对象。一个灯光设计师看到 Stage Plot，会马上知道你把主体放在哪里；一个音乐人看到 Cue Sheet，会知道视觉是在第几个段落进入；一个舞台管理看到 Cue List，会知道哪些动作需要被按顺序执行。

## 2.2 四种最低限度的文件

本课程使用四种最小工作文件：Stage Plot、Storyboard、Cue Sheet 和 Previs。它们不是行业里唯一正确的格式，也不追求专业制图精度，但各自回答一个清楚的问题。

| 文件 | 主要回答的问题 | 最低内容 |
|---|---|---|
| Stage Plot / Ground Plan | 东西在哪里？ | 观众方向、屏幕、人物/装置、主要灯位、关键尺寸 |
| Storyboard | 这一段先发生什么、后发生什么？ | 时间段、视觉中心、动作与空间变化 |
| Cue Sheet | 谁在什么时间做什么？ | 声音、人物/装置、灯光、屏幕/视觉的同步关系 |
| Previs | 这些关系放在一起是否成立？ | 可播放或可查看的空间/时间草稿 |

专业舞台设计会进一步包含 section、elevation、模型、props list、技术图纸等内容；数字媒体设计还会继续进入设备系统、投影机位置、mapping、masking、tech rehearsal 和 show report。[5] 本课程暂时不要求把这些全部掌握，但应知道它们存在，并能判断什么时候需要更专业的人加入。

## 2.3 “像导演一样想”应该怎样理解

工作坊里很容易出现一句诱人的话：“有了这些工具，大家都可以站到导演的角度。”这句话如果说得太满，会把真实协作简化成一种个人万能主义。更准确的表达是：当你开始同时观察空间、时间、表演、灯光和声音时，你会获得一种更完整的检查视角。它能帮助视觉创作者不再只问“屏幕里够不够酷”，而开始问“这一段演出为什么要在这里发生”。

这种视角并不取消专业分工，反而会让合作更有效。你知道自己缺什么，就更容易提出正确的问题：这里需要编舞判断，那里需要灯光师确认，这个段落需要音乐先定下来，某个互动机制需要技术团队验证。成熟的跨媒介创作，不是一个人包办所有角色，而是让不同角色在同一结构里工作。

# 第三章　时间结构：Cue、节奏与演出的推进

## 3.1 演出不是一组静态画面

舞台设计最容易被静态效果图误导。效果图可以证明某个瞬间很漂亮，却无法说明观众如何从前一个瞬间走到这里，也无法说明高潮之后怎样退回安静。现场真正发生的是时间。屏幕、灯光、声音和人物都在时间中进入、持续、变化、退出。

QLab 把 cue 定义为一个最基本的动作单元：一个 cue 发生一个事件；cue list 按顺序组织这些动作；cue sequence 则允许一次 GO 触发一连串同时或连续发生的事件。[3] 这种结构值得借鉴，因为它提醒我们：复杂的演出并不需要从“复杂”开始，它可以由很多清楚的小动作组织起来。

## 3.2 从“段落”而不是“效果”开始

初学者常用效果名来描述时间线：这里放粒子，那里闪一下，这里加 bloom。这样写很快，但很难判断结构是否成立。更可靠的写法是先给每一段一个功能，例如 OPEN、REVEAL、BUILD、PEAK、RELEASE。功能明确后，再决定灯、声音和屏幕分别如何完成这个功能。

这也是为什么 Opening 很适合作为第一道练习。它天然要求你保留余量：如果第一秒已经把所有屏幕、灯光和声音开到最大，后面就没有真正的推进。一个好的 Opening 未必复杂，它可能只是从几乎看不见的状态开始，让观众逐步意识到空间里有什么。

## 3.3 节拍与 Cue 不完全是一回事

音乐驱动的演出经常把 BPM 当成唯一时间单位，但现场并不总是按节拍机械运行。某些 cue 必须跟音乐 subdivision 对齐，另一些 cue 可能由演员动作、导演口令或现场判断触发。上一期“一键输入”工作坊讨论的 Press / Hold / Release 与 BPM 量化，适合处理可演奏的实时系统；本期的 Cue Sheet 则更关注不同媒介怎样在共同时间线上协调。

两者最终会汇合：一个 cue 可以触发一套状态，一个状态也可以在内部继续按 BPM 运行。理解这个层级以后，你会更容易处理实时视觉和线性演出的混合结构，而不是被迫在“完全预渲染”与“完全即兴”之间二选一。

> **作者札记｜为什么我会反复讲“该下去的时候要下去”**
>
> 做现场视觉时，我很容易被“持续有东西发生”吸引。尤其当控制器上有很多按钮和推子时，人会本能地想一直操作。但音乐真正有力量的地方往往来自前后的落差。画面如果始终亮、始终密、始终动，观众很快就会失去尺度感。
>
> 所以我后来把“能不能主动收掉”当成一个很重要的判断。不是因为极简本身更高级，而是因为只有前面真正留出空间，后面的变化才有分量。

# 第四章　预演的尺度：什么时候需要 3D，什么时候不需要

## 4.1 预演解决的是决策，不是虚荣

“我们是不是应该把整个场地完整建模？”这是最常见的问题之一。答案取决于你要解决什么。如果项目只需要一个固定观众视角，现场照片已经足够准确，而主要任务是验证一条视频放在屏幕里是否成立，那么一张正确透视的现场照片加上简单的 mask，可能比完整 3D 更高效。

只有当问题涉及多观看位置、遮挡、多屏关系、空间移动、XR、灯光与对象关系，或者你需要让团队在不同角度共同检查时，完整 3D 才开始产生明显收益。Vectorworks 的 previz 工作流本身也建立在“先建真正需要的场景与设备，再进入可视化和 cue 测试”的思路上，而不是要求所有项目都做同样复杂度的模拟。[2]

## 4.2 写实程度与判断质量

高写实度有时会提高沟通效率，例如客户很难从灰盒理解空间时；但它也可能制造“已经定稿”的错觉。一个过早做得很漂亮的模型，会让团队不愿意推翻结构。相反，粗糙但清楚的草稿更容易被修改。

因此我倾向把写实程度当成一种沟通变量。内部讨论结构时，Gray Box 足够；需要确认屏幕反射、灯光氛围或对外提案时，可以逐步提高材质与光照质量。不要因为工具能渲染，就默认渲染越真实越好。

## 4.3 浏览器预演的特殊价值

浏览器最大的优势不是画质，而是共享成本低。一个链接可以在不同设备上打开，屏幕 source 可以直接替换，WebXR 还允许把场景放进头显观看。它很适合作为跨软件的“中间层”：视觉作者继续在 TouchDesigner、Blender 或 Processing 里工作，音乐人继续在 Ableton 里工作，场景页面只负责把各自结果放回空间关系里。

这也解释了为什么 Scene Forge 不应该试图复制专业 CAD、DAW 或灯光控台。它更像一个可共享的草稿桌：足够轻，才能在项目早期被频繁打开；足够结构化，才能让不同角色看到同一组问题。

# 第五章　把自己的媒介带进场景

## 5.1 不同背景的人应该从不同入口进入

10 月 31 日的参与者中，有人做实体装置，有人做音乐，有人做 VR，也有人希望为自己的乐队做视觉。现场反馈里有一位装置方向的参与者，一开始并没有立刻把自己和屏幕视觉联系起来；当她把自己的装置放进预演场景后，才突然找到乐趣。这个反馈说明的并不是课程“太偏屏幕”，而是入口设计不够清楚。

同一套方法应该允许不同媒介成为主角。音乐人可以从曲式和节拍进入；装置创作者可以让屏幕几乎保持空白，把对象放在空间中心；灯光方向的人可以先研究照度、方向和空间层次；视觉作者则可以把已有网页、视频或实时程序放进屏幕，再检查它是否真的需要占据这么多注意力。

## 5.2 案例札记：ENTROPY 的上下屏关系

ENTROPY 的现场有主屏和顶部屏。最初真正有价值的问题不是“顶部屏做什么新素材”，而是两个屏幕能不能形成同一个相机世界。于是空间草稿先确认屏幕角度和衔接关系，再决定内容如何跨越折角。这个过程中，网页预演的价值很直接：不需要等到现场搭建完成，团队已经可以判断上下关系是否顺、视觉中心是否被拉散。

这样的多屏项目特别适合预演，因为单块屏幕里看似成立的构图，到了空间里可能会因为视角和折角被完全改变。反过来，如果项目只有一个固定正视角，花大量时间模拟所有空间细节未必值得。预演的复杂度应当由问题决定。

## 5.3 案例札记：Timer 与一个光源

Timer 的一个版本里，我在屏幕后方只放了一个主要光源，并把光的强度绑定到音量变化。这个做法没有复杂的灯光系统，却意外强化了屏幕和空间之间的距离感。它提醒我，空间感不一定来自更多元素，有时候来自一个关系被处理得足够明确：屏幕不是独立发光的矩形，而是整个空间光环境的一部分。

## 5.4 案例札记：“不断向前”的隧道与扫描

另一个工程《不断向前》使用隧道式点云和扫描结构，现实场地又具有前后递进的屏幕关系。画面从空间里“刷过去”时，数字隧道的运动方向与真实屏幕的深度关系互相强化。这里真正有效的不是某个 shader，而是虚拟空间的运动逻辑和真实场地的几何逻辑说了同一种话。

## 5.5 案例札记：卫星线框与实时工程

卫星和航天器的线框项目则更接近实时“信息仪器”。不同飞行器可以切换，顶部屏与主屏共享一个世界，排列方式会变化，视觉语言故意保留一种老式科学终端的 nerd 气质。这样的项目不一定需要完整叙事，却非常依赖状态和控制：什么内容可以切、哪些参数需要现场操作、如何在不破坏整体风格的前提下变化。它与“一键输入”课程中的 Mapping 思想直接相连。

> **跨模块联系｜从一键输入到场景铸造**
>
> 一键输入训练的是“一个动作怎样进入状态、节拍、声音和视觉”；场景铸造训练的是“这些状态最终怎样进入空间和时间”。当两者连接起来，网页、控制器和舞台不再是三套东西，而是同一个系统的不同层。NIME 领域把 Mapping 视为电子乐器设计的核心之一——输入与系统参数之间的关系，会直接决定一件数字乐器的性格。[6] 这个观点同样适用于实时演出系统。

# 第六章　从参考到 V2：一个可复用的工作流程

## 6.1 参考不是风格拼贴

很多创作从 Pinterest、演唱会截图或艺术家作品开始，这是合理的。但参考的作用不是告诉你“做得像谁”，而是帮助你识别结构：这个空间为什么成立，观众的注意力被放在哪里，哪个元素先出现，灯光怎样改变尺度，什么东西在高潮前被保留。

专业设计训练同样强调 research 与 conceptual development。CMU 的 scenic design 课程把 in-depth research、scriptual examinations、space arrangement、composition 和 groundplan 放在一个连续过程中。[4] 对我们来说，最重要的不是复制学校课程，而是借用这种顺序：先理解问题，再选择形式。

## 6.2 先画草图，再让工具工作

手绘、简单框图或几句话的时间结构，通常比一开始直接生成完整 3D 更有价值。工具擅长把明确关系做得更快，却不擅长替你决定“为什么这个主体要在这里”。如果输入只有一句“做一个很酷的未来舞台”，最后往往只能得到平均化的视觉。

在工作坊现场，我会鼓励大家用语音把问题一次讲清楚，再把截图、场地和草图一起交给工具。真正有效的部分不是“长提示词”本身，而是创作者必须先把自己的判断说出来。只要你能明确指出“这个屏幕不该透明”“主视角太低”“折角应该连续”“顶部光应该晚两秒进入”，工具才有机会成为实现助手。

## 6.3 第一版必须尽快出现

第一版的目的不是好看，而是让错误尽早暴露。一个 10—20 分钟的 Gray Box，往往比两个小时的精细建模更适合第一次评审。看见结果以后，先停止继续加东西，回答一个具体问题：比例不对、推进不清楚、空间没有层次，还是音乐与画面同时抢注意力？

## 6.4 版本控制是一种创作记忆

当项目由代码、网页或多个软件组成时，版本控制不仅是程序员的习惯，也是一种创作记忆。尤其在使用生成式工具辅助改代码时，上下文可能会把已经正确的部分改坏。每个阶段留下可回退的版本，能让团队知道“哪一次修改导致了问题”，也能把错误积累成下一次项目的经验。

这和专业制作中的 show file、cue list、tech note、show report 有相似精神：现场系统必须能被重复、检查和恢复。真正可靠的工程不是从不出错，而是出错以后知道怎样回到一个稳定状态。

# 第七章　失败、版本与现场风险

## 7.1 一个打开错工程的现场事故

我有一次演出使用 Blender 实时工程，到了现场却不是自己的电脑。因为文件没有完整确认，我打开了错误的工程；原本实时运行的部分在切换到预渲染素材时出现了资源丢失，画面直接变成紫色。第一次没有放出来，第二次依然失败。这个事故很难用“创意不好”解释，它完全属于生产流程：文件、依赖、版本和现场机之间没有被彻底检查。

这类问题最适合进入教材，因为它能让抽象的“版本管理”“预检”“备份”变成具体经验。一个漂亮的预演如果没有 deployment plan，现场依然可能崩溃。相反，一个画面并不复杂、但有明确 fallback 的系统，往往更适合真实演出。

## 7.2 现场风险至少分三类

| 风险类型 | 典型问题 | 应对思路 |
|---|---|---|
| 创作风险 | 结构平、高潮无差异、媒介互相抢 | 在预演阶段用 critique 提前暴露；V2 只改一项 |
| 技术风险 | 文件缺失、依赖断裂、分辨率/接口不匹配 | 预检、版本冻结、备用视频/静态图、恢复路径 |
| 协作风险 | 谁负责什么不清楚、cue 口径不同、现场临时改动无法同步 | Cue Sheet、负责人、变更记录、技术彩排 |

## 7.3 Panic、Reset 与 fallback

实时系统里常被忽略的一部分，是怎样停止。上一期“一键输入”里强调 Panic / Reset / Resync，是因为一件可演奏系统必须允许操作者从失控状态回来。场景预演和现场播放同样需要 fallback：如果实时 source 不工作，能不能切到预渲染视频；如果顶部屏失效，主屏版本是否仍然成立；如果网络断开，控制是否还能在本机继续。

这些设计不会让作品变得更炫，却会显著提高它被真正演出的概率。专业 show control 的 cue 体系之所以强调状态、顺序和可重复执行，也正是因为现场不是一次性的演示，而是要在压力下稳定工作。[3]

> **现场预检 / Preflight 的最低版本**
>
> 至少提前确认：场地屏幕规格与实际输出；主工程和备份工程；所有外部媒体路径；字体与插件；音频设备与采样率；控制器和 MIDI / OSC；网络依赖；现场机器 GPU / 浏览器版本；一键黑场 / Stop；不用实时系统时的备份视频。
>
> 预检表不需要写得像航空手册，但必须让另一个人也能照着检查。

# 第八章　标准练习：30 秒 Opening

这一章把前面的概念收束为一条完整练习。它的目的不是做出一段“标准风格”的视觉，而是第一次完整经历：场地、Stage Plot、时间结构、Cue Sheet、预演、评审和 V2。练习选择 Opening，是因为开场最容易暴露信息量、节奏和空间层次的问题。

## 8.1 情境设定

假设你要为一个小型黑盒空间设计 30 秒开场。现场有一块中央主屏、一个可选顶部屏、一位表演者或一个装置主体、一条主要灯光方向。音乐还没有最终完成，但你知道整体情绪应该从安静进入明确节奏，并在 24—30 秒出现第一次强烈汇合。

如果你的方向是书法，可以把“主体”理解为一组笔画；如果做实体装置，可以让装置成为主体而弱化屏幕；如果做音乐，则先把自己的 8 / 16 bar 结构换算成下面的时间段。练习的结构不变，材料可以替换。

## 8.2 Stage Plot

先画一个极简平面：观众在下方，中央屏在舞台后部，表演者/装置位于中心偏前，一条主光从后上方指向主体。顶部屏作为空间扩展层，不承担第一秒的视觉中心。此时不要讨论材质。只检查主体、屏幕和观众之间的距离是否合理。

## 8.3 Storyboard：先写每一段的功能

| 时间 | 功能 | 场景变化 |
|---|---|---|
| 00–06s | OPEN | 黑场或极弱环境；不急于交代主体 |
| 06–12s | REVEAL | 第一笔 / 主体出现；主光建立；声音出现第一层材料 |
| 12–18s | BUILD 01 | 增加第二层信息，但保持空间集中 |
| 18–24s | BUILD 02 | 空间开始展开；人物/装置发生第一次明确变化 |
| 24–30s | PEAK | 声音、灯光、屏幕第一次完整汇合 |
| 30s+ | RELEASE | 拿掉至少一层，为下一段留下空间 |

## 8.4 Cue Sheet：把不同媒介放到同一张表里

| Time | Sound | Performer/Object | Light | Screen |
|---|---|---|---|---|
| 00–06 | 极弱 ambience | 静止 / 不出现 | 0–5% | 黑场 |
| 06–12 | texture | 出现 / 唤醒 | 10–20% 主光 | 中央内容 fade in |
| 12–18 | pulse | 保持 / 小动作 | 20–30% | 第二层内容进入 |
| 18–24 | rhythm | 移动 / 展开 | 40–60% | 空间关系展开 |
| 24–30 | 明确 hit | 停 / 锁定 | 70–100% / flash | 第一次完整汇合 |
| 30+ | release | 静止 | 回落 | 删去至少一层 |

## 8.5 V1 的典型问题

第一次做出来以后，最常见的问题不是“效果不够多”，而是所有东西都太同步：音乐一抬升，灯光、屏幕和人物同时变化；下一段又一起变化。结果看似整齐，却没有真正的层次。另一个常见问题是 Peak 不够明显，因为前面亮度和密度已经用得太满。

因此 V2 只做一个改动：把顶部屏的进入延后两秒，同时把 18 秒之前的灯光上限压低。这样 Peak 不需要额外增加效果，也会因为前面留出了更多空间而显得更强。这个修改比“再加一个粒子系统”更有价值，因为它直接解决了结构问题。

## 8.6 提交与评审

完成练习后，提交的不是一张最终图，而是一组能证明你经历过设计过程的材料：Stage Plot、Storyboard、Cue Sheet、10—30 秒预演录屏、V1 与 V2 的对比，以及一句话说明“第二版只改了什么”。评审时先讨论结构，再讨论风格。

> **练习判定**
>
> 通过标准不是“像专业演唱会”，而是：第一秒没有过满；第一件材料出现得清楚；12—24 秒确实在推进；Peak 与前面有明显差异；人物/装置与屏幕不是互不相关；Release 真的拿掉了东西；V2 能说明具体修改。

# 第九章　把一次工作坊变成长期训练

## 9.1 线下负责密度，线上负责重复

一次三小时工作坊很难同时完成理论、软件、案例、实践和作品。更合理的分工是：线下负责示范、批评、同伴交流和真实设备体验；线上负责重复练习、补课、版本保存和提交。只有允许参与者在课后重新做，课程才可能从“体验”变成“能力”。

这也是为什么本系列会逐步发展成能力地图，而不是不断增加新的工具课。每一关只多一个能力：先跟做，随后只改一个变量，再把几个状态组织成一段时间结构，然后加入跨工种协作，最后进入真实场地。

## 9.2 五级训练

| 等级 | 任务 | 核心判断 |
|---|---|---|
| L1 COPY | 严格完成标准答案 | 能不能走通一次完整流程 |
| L2 MODIFY | 只改一个变量 | 能不能说清楚为什么改 |
| L3 COMPOSE | 独立编排 20–30 秒 | 是否有推进、留白和收回 |
| L4 COLLAB | 加入声音/灯光/表演/装置 | 不同媒介是否在同一结构里工作 |
| L5 PERFORM | 进入真实场地测试 | 是否能运行、恢复、记录和复盘 |

## 9.3 评价不只看“好不好看”

视觉质量当然重要，但它不应该成为唯一标准。对初学者更有帮助的评价维度包括：结构是否读得懂，时间是否成立，多媒介关系是否清楚，系统是否可控制和恢复，是否真的根据反馈做过修改，以及别人能不能从你的文档复现项目。

这种评价方式会把“审美天赋”从唯一中心移开。一个画面暂时不漂亮的学员，也可能已经建立了很好的工作结构；一个视觉非常强的学员，也可能因为缺少文档和版本管理，在真实项目里难以合作。两者都需要被看见。

# 附录 A　工作模板

## A.1 Stage Plot 最小字段

- 场地边界与观众方向
- 主屏 / 顶屏 / 侧屏的位置与大致尺寸
- Performer / Object / Installation 的位置
- 主要灯光方向或关键灯位
- 入口、出口、遮挡与不可占用区域
- 尚未确认的数据用明确标记注明

## A.2 Storyboard 最小字段

- 时间范围
- 这一段的功能
- 视觉中心
- 主体动作 / 位置变化
- 空间变化
- 与上一段相比增加了什么、减少了什么

## A.3 Cue Sheet 最小字段

- Cue 编号或时间
- Sound / Music
- Performer / Object
- Light
- Screen / Visual
- 触发方式（GO / time / BPM / manual / sensor）
- 备注与 fallback

## A.4 预检清单

- 最终屏幕规格与实际输出一致
- 主工程、备份工程与预渲染 fallback 均可打开
- 媒体、字体、插件、模型路径完整
- 音频设备、采样率与输出通道确认
- MIDI / OSC / 网络依赖检查
- Panic / Stop / Blackout 可用
- 现场机器性能与浏览器/软件版本确认
- 至少完成一次从头到尾的冷启动测试

# 附录 B　阅读地图

阅读材料分为“必要”和“补充”。必要阅读用于建立生产语言；补充阅读用于扩展视野，不建议在第一次练习前全部读完。

## B.1 必要阅读

- Alex Oliszewski, Daniel Fine, Daniel Roth, Digital Media, Projection Design, and Technology for Theatre, 2nd ed., Focal Press, 2025。重点看 design process、cue list、previsualization、tech week 与 documentation。
- Yale Undergraduate Production: Scenic Designer。重点看 ground plan、section、elevation 与设计修订时间线。
- QLab 5 Documentation: Cues, Cue Lists, Cue Sequences。重点理解 cue 作为动作单元，以及线性顺序与序列。
- Vectorworks Spotlight: Previsualization / Showcase workflow。重点理解 previz 在 load-in 前承担什么决策。

## B.2 补充阅读

- J. Michael Gillette, Rich Dionne, Theatrical Design and Production, 9th ed., McGraw Hill, 2024。作为舞台设计与制作的综合入门。
- Peter Brook, The Empty Space。用于重新思考舞台、观看与表演的基本关系。
- Andy Hunt, Marcelo Wanderley, Matthew Paradis, “The Importance of Parameter Mapping in Electronic Instrument Design,” NIME 2002。与“一键输入”及实时控制模块直接相关。
- Carnegie Mellon School of Drama Scenic Design curriculum。用于理解专业训练如何把研究、空间、制图、模型和协作连接起来。

## B.3 不建议作为主课前置的内容

完整灯光控台编程、复杂 DMX 网络、专业 CAD 出图规范、角色动画、完整 DAW 编曲、Unreal / Blender 高级渲染，都可以在项目需要时进入，但不应成为初学者完成第一条预演的门槛。课程越早把所有专业知识一次性塞进来，越容易重演“自由度太高却不知道从哪里开始”的问题。

|---|---|
