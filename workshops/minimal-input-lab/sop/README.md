# Minimal Input Lab SOP
## 极简输入实验室｜标准操作流程

SOP 不是课程正文的替代品，而是把课程里的方法压缩成可以重复执行的工作流程。

Reader 负责回答：为什么这样做、这个方法从哪里来、真实项目里发生过什么、什么情况下应该换一种方法。

SOP 负责回答：现在从哪里开始、下一步做什么、做到什么程度才算通过、出了问题退回哪一步。

## 使用原则

每一条 SOP 都遵循同一结构：

1. **Purpose / 目的**：这一条 SOP 解决什么问题。
2. **When to Use / 适用情境**：什么时候该使用，什么时候不该使用。
3. **Inputs / 输入**：开始前必须准备什么。
4. **Outputs / 输出**：完成后必须留下什么。
5. **Procedure / 步骤**：按顺序执行，不把关键判断藏在经验里。
6. **Gate / 关卡**：每一步都要有通过条件。
7. **Failure Modes / 常见失败**：遇到什么情况说明应该停下来，而不是继续加东西。
8. **Recovery / 恢复**：失败后退回哪一步，怎样恢复到稳定状态。
9. **Record / 记录**：版本、截图、录屏、修改原因。

## 当前 SOP 地图

### SOP-01｜从 Brief 到 Gray Box
把一个模糊的演出需求转换成可讨论的空间草稿。

### SOP-02｜30 秒 Opening：从 V1 到 V2
完成第一条空间 + 时间 + 声音 + 光 + 屏幕 / 对象的完整演出结构。

### SOP-03｜现场预检与 Fallback
在真实演出前检查文件、媒体、设备、控制和备用方案。

### SOP-04｜一次 Critique 怎么进行
避免“好不好看”的空泛评价，把反馈转成下一版的单一修改任务。

## Reader 与 SOP 的关系

推荐结构：

```text
READ
理解问题与情境
↓
SOP
照步骤完成一次
↓
CHECKPOINT
停下来检查
↓
CRITIQUE
只找最严重的问题
↓
V2
只改一个关系
↓
RECORD
保存证据与版本
```

SOP 的目标不是把创作变成流水线，而是把那些本来靠“做久了自然知道”的基础动作显性化。只有基础动作稳定以后，自由发挥才真正有意义。
