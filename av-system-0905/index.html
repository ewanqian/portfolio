00 / CONTEXT

这堂课接在 8.29 之后：从“一个控制怎样工作”继续到“整套演出怎样工作”

8.29 的工作坊已经研究过 Tap / Hold / Release、BPM、State、Mapping，以及怎样把一次控制变成声音和视觉的共同反馈。9.5 把视角拉远：现场里会同时存在音乐、时间、多个视觉模块、多个状态、控制器、软件和表演者。系统设计处理的是这些东西之间的关系。

01 / REFERENCE

先看一位艺术家为什么花数月制作自己的演出系统

Pauric Freeman 在 2025 TouchDesigner Dublin 分享了自己的 audiovisual performance system。他讨论的重点包括声音数据怎样进入视觉、场景怎样保存和召回、不同视觉元素怎样切换和组合，以及怎样让这些操作在一场长时间演出里保持可靠。

听的时候先注意：数据从哪里来？

声音、MIDI、控制器、程序内部参数，都可能成为视觉系统的输入。这里先观察关系，不需要理解 TouchDesigner 节点。

注意：他为什么要保存 Scene？

现场里常常需要把一整组参数重新叫回来。Scene 的价值来自“召回一套状态”，而不是单独切一个画面。

注意：为什么会谈 Permutation？

已有的视觉元素可以重新排列组合。长时间表演的变化不完全依赖不断制作新素材。

注意：为什么稳定性被反复提到？

现场切换发生在观众面前。加载卡顿、状态不明、无法恢复，都会直接变成演出问题。

02 / WHY SYSTEM

当内容从几条视频增加到很多状态以后，表演者需要知道“现在在哪里”

VJ 最常见的起点是播放视频：选一条 Clip，调整速度、透明度或效果，再切到下一条。内容数量少的时候，人可以靠记忆管理。实时视觉工程越来越多以后，记忆很快会失效。

只有少量素材时

“这条视频适合重拍，那条适合 Break。”表演者可以在脑内记住素材位置和用途。

有很多实时模块以后

一个工程可能有多个视觉状态、多个 Layer、MIDI、BPM、参数范围和恢复方式。操作开始需要结构。

系统至少要能回答： 现在音乐走到哪里？ 现在有哪些 Layer 正在运行？ 当前是哪一种 State？ 这个 MIDI / Audio 信号控制什么？ 下一次变化什么时候执行？ 哪些内容可以同时存在？ 出问题以后怎样 Reset / Panic？

系统的价值首先体现在“可观察”和“可恢复”。表演者在高压现场里需要快速知道当前状态，并且可以进入、退出、增加、减少、召回和重置。

给讲者：这一段讲到哪里
  • 用自己的 Resolume Deck 或 Processing 文件数量举例。尽量说具体数量和操作，不讲抽象的软件架构。
  • 让听众想象：十个工程，每个有五个状态，已经是五十种可能。再加 BPM、MIDI 和 Layer，人的记忆会成为瓶颈。
  • 此时再引入“State、Layer、Routing”三个词。只报名字，后面分别解释。
这一节的结束条件：听众能说出“为什么直接放视频有时够用，以及内容规模变大以后哪里会开始失控”。
03 / LIVE ENVIRONMENT

Audio Visual 的现场环境里，音乐不一定会把数据主动交给视觉

先把一个常见误会清掉：现场里听得到音乐，不代表视觉程序已经拿到了音乐数据。音响播放出来的声音、DJ 设备内部的音乐时间、MIDI 消息、电脑里的音频波形，是几条不同的信息通道。

DJ / LIVE ELECTRONICS / INSTRUMENT / AUDIO FILE │ ↓ MUSIC │ ┌────────────────┼────────────────┐ ↓ ↓ ↓ 人的耳朵 设备的音乐时间 数据接口 Listening / Judgement BPM / Beat MIDI / Audio │ │ │ └────────────────┼────────────────┘ ↓ VISUAL SYSTEM

情况一：视觉表演者自己听

音乐进入 Break，表演者听见空间突然变空，于是减少画面；Bass 进入以后，切到更重的视觉状态；音乐突然停顿，画面 Freeze 或 Black。这里没有任何自动音乐分析，Audio Visual 仍然成立，因为人的判断承担了音乐理解。

情况二：音乐设备提供时间或控制信号

视觉程序收到 BPM、Beat、MIDI Note、MIDI CC 等信息以后，可以把一部分重复且精确的工作交给系统，例如每拍脉冲、每小节切换、某个鼓点触发 Accent。

情况三：视觉端直接分析音频

麦克风、声卡 Loopback 或音频接口把实际声音送给程序。程序可以分析整体音量、低中高频、瞬态或频谱。这类数据反映“声音现在长什么样”，但它不会自动理解音乐叙事。

给讲者：这一段讲到哪里
  • 先问现场：“如果我现在在旁边听一位完全没排练过的 DJ，我怎么做视觉？”答案往往就是耳朵和经验。
  • 再问：“如果 DJ 电脑愿意给我 BPM，我可以少做哪一部分工作？”把答案引到时间同步。
  • 最后才提音频分析，让大家知道它只是众多数据来源中的一种。
这一节的结束条件：听众不会再把“Audio Visual”理解为“FFT 可视化”；他们知道人、音乐时钟、MIDI、音频分析都能形成连接。
04 / THREE KINDS OF INFORMATION

把现场信息整理成三类：时间、事件、连续数值

程序需要明确的数据。为了让后面的视觉模块容易复用，可以先不关心数据来自哪个设备，只看它表达什么。

TIME

现在走到哪里？

BPM、Beat、Bar、Phase、Phrase。它们建立共同的音乐时间坐标。

EVENT

刚才发生了什么？

Kick、MIDI Note、Cue、Trigger、Scene Change。通常表现为一次离散事件。

VALUE

现在有多少？

音量、低频能量、MIDI CC、Envelope、LFO。通常整理成 0.0 到 1.0。

0 / 1：适合表达一次事件

KICK 0 0 0 1 0 0 0 1 MIDI NOTE 0 → 1 → 0 TRIGGER false → true → false

0.0–1.0：适合表达连续变化

MIDI CC 0 ───────── 127 normalize ↓ SYSTEM VALUE 0.0 ──────── 1.0 例如： density = 0.72 energy = 0.41 space = 0.18

“0–1”没有规定视觉一定怎么动。它只是一个方便交换的范围。今天的 density = 0.72 可以来自 MIDI Fader，明天也可以来自 Bass Energy；视觉模块只负责解释这个数值。

一个实用判断：如果一条信息回答“有没有发生”，先把它当 Event；如果回答“现在有多少”，先把它当 Value；如果回答“音乐走到哪里”，放进 Time / Transport。

给讲者：这一段讲到哪里
  • 一定要用一个真实旋钮演示 0–127，再口头换算成 0–1。不要先讲 normalize 的数学定义。
  • Event 可以拿 Kick 或 MIDI Note 举例；Value 用 Fader 或音量最容易理解。
  • 提醒大家：TIME 单独列出来，是因为现场演出经常需要 Beat / Bar / Phrase 这种共享坐标。
这一节的结束条件：给听众任意一个信号，他们大致能判断它属于 Time、Event 还是 Value。
05 / SHARED CLOCK

BPM 给系统一把共同的尺子：Beat、Bar 和 Phrase 都从这把尺子往上建立

BPM 是 Beats Per Minute，每分钟多少拍。120 BPM 意味着每秒大约两拍。舞曲里常见四拍组成一小节；多个小节再形成更长的 Phrase。视觉只要共享这套时间，就可以在稳定的音乐边界上发生变化。

Phase

Phrase
更长的音乐结构单位。大型变化通常更适合发生在 Phrase 边界。

Ableton Link 在这里解决什么？

Link 让兼容设备或软件在局域网里共享音乐时间。它同步 musical beat、tempo 和 phase。Resolume 加入同一个 Link session 后，会跟随共同 BPM 和 measure position。Link 本身不负责把整段音乐音频送给视觉，也不会告诉视觉“这段 Bass 很重”。

没有 Link 怎么办？

Resolume 可以直接 Tap BPM：视觉表演者听着音乐点击 Tap，建立大致速度，再在新的 Phrase 第一拍 Resync。很多现场就是从这种人工同步开始。MIDI Clock 也可以发送时间信息，但不同协议在稳定性和延迟上有不同表现。

06 / DJ SYSTEM

专业 DJ 环境还能把 Waveform、Beatgrid、BPM 和播放时间交给 FOH 系统

当演出使用支持 PRO DJ LINK 的 Pioneer DJ / AlphaTheta 设备时，舞台另一端可以获得比“只听声音”更丰富的信息。Stagehand 的 Waveform 页面能够远程显示正在播放曲目的 waveform、beatgrid、BPM 和 time information，用于帮助灯光与视觉团队判断音乐结构。

CDJ / DJM │ ├── Waveform ├── Beatgrid ├── BPM ├── Playback Time └── Player / Mixer Status ↓ PRO DJ LINK NETWORK ↓ FOH / LIGHT / VISUAL

PRO DJ LINK Bridge 则用于把专业 DJ 系统与经过认证的灯光、视频或其他 show-control 产品连接起来。这里最值得记住的是：**不同现场能拿到的音乐信息不同。** 有的现场只有耳朵，有的有 BPM，有的有 MIDI，有的可以读取完整 DJ playback metadata。

系统设计的现实条件：视觉工程最好知道“自己依赖哪些信号”。如果唯一依赖某种 DJ metadata，换到没有该设备的场地就会失效；如果保留 Manual / Tap / MIDI 等 fallback，同一套视觉更容易进入不同演出环境。

08 / ARCHITECTURE

把“很多视觉”组织成系统，可以从 Material、Layer、State、Show 四个层级开始

层级的作用是把不同时间尺度的问题分开。一个视觉行为可能只持续一秒，一条 Layer 可以持续整段音乐，一个 State 会同时调整多条 Layer，而 Show 负责更长时间的推进。

MATERIAL / BEHAVIOUR 一个可以被调用的声音或视觉行为 ↓ LAYER 一条持续可用的演出通道 ↓ STATE 多条 Layer + 参数当前的组合 ↓ SHOW State、Transition 与人的决定怎样形成整场演出
Material
一段 Clip、一个 Processing Visual、一个 Shader、一个 Pulse 行为、一个 Texture。它回答“我手上有什么材料”。
Layer
可以持续开启、关闭、混合和控制的一条通道。它回答“这些材料以什么角色同时存在”。
State
一组当前关系：哪些 Layer 开着、参数是多少、时间分辨率多细、哪些输入有效。它回答“系统现在是什么样”。
Show
多个 State 在一段较长时间里的顺序、可达路径、自动与人工决定。它回答“整场演出怎么走”。

仓库里的 Browser Performance Runtime 研究使用了更完整的层级：Asset → Capsule / Cell → Clip → Sequence → Layer → State → Show。课堂先使用四层版本，已经足够把“素材”与“演出结构”分开。

给讲者：这一段讲到哪里
  • 不要让大家背层级。拿一套现成视觉指着讲：这个 Loop 是 Material；放在 Arena 第二层以后它成为 Layer；三层共同的配置叫 State。
  • 最后把多个 State 连接成一场 30 分钟演出，才进入 Show。
  • 如果听众已经理解四层，就不继续展开 Capsule、Sequence 等细节。
这一节的结束条件：听众能区分“一个素材”“一条长期通道”“一套当前状态”“整场演出结构”。
09 / STATE

State 的作用是一次改变一组关系，让系统在不同音乐段落里表现得不同

如果每次进入音乐 Break 都要手动关五个 Layer、改三个参数、换一个 Visual Bank，现场操作会越来越脆弱。State 可以把这些关系保存成一组可召回配置。

同样一套控制器，在 HEAVY 和 BREAK 两种 State 下可以拥有不同意义。视觉素材没有全部更换，系统对它们的组织方式改变了。

State 设计时先问：进入这个状态以后，哪些东西应该出现？哪些应该退出？密度、速度、释放时间和时间分辨率怎样变化？操作者怎样知道自己已经进入？怎样离开？

  • 用你现场最常用的“空 / 中 / 重”或者 Intro / Build / Peak 例子替换也可以。

10 / LAYERS

Layer 让视觉可以持续存在、互相叠加，也让每条通道承担不同演出角色

一场演出不需要每次变化都把整张画面换掉。把内容分成几条角色明确的 Layer，可以保留连续性，也方便 State 去控制“加什么、减什么”。

L1 · BASE

长期存在的空间、纹理、背景结构。它给画面一个连续的地面。

L2 · RHYTHM

和 Beat / subdivision 关系明显的动态层。可以随 Build 增加密度。

L3 · ACCENT

为 Drop、Hit、特殊事件准备的短暂强调。默认可以保持 Ready 而不持续占画面。

L4 · TRANSITION

进入、退出、遮挡、Blackout、空间转换时使用，帮助两个状态之间有过程。

STATE A BASE ON RHYTHM LOW ACCENT READY TRANSITION OFF ↓ 进入更高能量状态 ↓ STATE B BASE ON RHYTHM HIGH ACCENT ACTIVE TRANSITION OFF
给讲者：这一段讲到哪里
  • 最好打开 Resolume 的 Layer 列表边讲。它能把“Layer”从抽象概念直接变成软件里的实际通道。
  • 讲角色，不讲固定数量。四层只是教学例子，真实项目可以更少或更多。
  • 提醒：Layer 的意义来自“它在演出中负责什么”，不只是素材被放在哪一层。
这一节的结束条件：听众知道 Layer 可以让变化发生在局部，而 State 可以一次管理多条 Layer。
11 / ROUTING

Routing 决定一条信号在当前状态里应该去控制谁

如果 Bass Energy 永远只控制 Scale，系统很快会显得机械。Routing 允许同一个信号在不同上下文里进入不同目标，也允许一个目标综合多种来源。

BASS ENERGY ↓ ROUTER │ ├── STATE A → VISUAL SCALE ├── STATE B → DENSITY └── STATE C → CAMERA PRESSURE
MIDI NOTE 36 ↓ ROUTER │ ├── BUILD → ADD PULSE └── PEAK → FLASH / ACCENT

Routing 让“输入设备”和“视觉实现”松开绑定。今天 MIDI Note 36 来自鼓机，明天可以换成键盘、OSC 或网络消息；只要它被转换成同一个语义动作，系统后面不必重写。

Graph / Route：当 State 越来越多

如果状态数量增加，可以进一步规定哪些状态之间可以自然迁移。仓库里的 Graph / Node / Route 方法把效果改写成演出角色，再建立可达路径。例如 FIELD → PULSE → ROUTE → ORBIT → RELEASE。这样表演者不仅知道“当前是什么”，还知道“下一步可以去哪里”。

Graph / Node / Route 方法 ↗
给讲者：这一段讲到哪里
  • 先讲一个最小 Router：Bass 在两个 State 里控制不同参数。
  • 只有当大家已经接受“同一个信号可以重新指向”以后，再讲 Graph。
  • Graph 不必现场实现；它承担的是“很多 State 之间怎样走”的下一层问题。
这一节的结束条件：听众知道 Mapping 可以被 State 改写，系统因此拥有上下文。
12 / HUMAN + AUTOMATION

系统负责精确和重复，人负责判断这一刻应该发生什么

自动同步越多，并不意味着现场的人越不重要。BPM、Beat、MIDI、Audio Analysis 可以帮助系统保持时间、触发细节和安全边界；表演者仍然决定方向、克制、段落和意外。

MUSIC ↓ TIME / EVENT / VALUE ↓ SYSTEM ↙ ↘ AUTOMATION HUMAN 精确 / 重复 判断 / 方向 ↘ ↙ VISUAL STATE ↓ STAGE
系统适合负责

BPM、Clock、Quantize、最大视觉密度、最大声音数量、参数范围、Transition Scheduling、Reset / Panic。

人适合负责

这个 Drop 要不要跟？这一段需不需要空？现在继续当前视觉还是换？哪些素材应该留下？什么时候提前准备下一段？

面对不熟悉的 DJ set，人还承担实时音乐理解。面对排练充分、信号完整的合作演出，系统可以承担更多可预测的工作。两种模式可以共存。

给讲者：这一段讲到哪里
  • 讲一个你真正“忍住没跟 Drop”的例子，这比抽象谈 Human-in-the-loop 更容易理解。
  • 再讲一个系统应该自动完成的事情，例如 1/8 quantize 或 density cap。
  • 最后让大家看到：自动化和人工判断是职责分配，不是一条从“手动”走向“全自动”的单向升级。
这一节的结束条件：听众可以说出至少一件应该交给系统的事，以及一件应该留给表演者的事。
13 / RETURN TO FREEMAN

现在回看 Freeman：Data Formatting、Scene Recall、Permutation 和 Always Rendering 都有具体用途

Data Formatting
不同来源先整理成系统能够重复使用的 Time / Event / Value。设备更换时，后面的视觉逻辑不需要全部跟着重写。
Scene Storage / Recall
保存一整组参数与元素关系，现场需要时可以完整召回。它解决“我刚才那套状态怎么回去”的问题。
Permutation
已经存在的元素重新组合。变化来自组合关系，因此系统不必用无限新增素材维持长时间演出。
Always Rendering
需要快速切换的元素保持运行或预备状态，避免现场第一次调用时加载、编译或初始化造成停顿。

判断一个系统方法有没有价值，可以问：它解决了哪一个现场问题？它减少了什么记忆负担？它怎样帮助状态召回、时间同步、内容组合、故障恢复或排练重复？

给讲者：这一段讲到哪里
  • 这一段是对开场视频的“二次观看”。此时大家已经有词汇，可以把 Freeman 的方法对应到自己刚学的结构。
  • 每一个术语都配一个现场失败场景：Recall 失败会找不回状态；Always Rendering 不成立会卡顿。
  • 不继续延伸 TouchDesigner 实现细节，保持在 system design 层。
这一节的结束条件：听众能把 Freeman 的四个关键词翻译成现场里会遇到的具体问题。
14 / LIVE DEMO

最后打开真实工程，只追踪三条链：时间、控制、状态到输出

复杂工程不需要从第一行代码开始解释。听众已经有了 Clock、Event、Value、Layer、State、Routing 这些概念，现场只需要把它们在真实项目里的位置指出来。

链 1 · TIME

BPM → Transport → Beat / Bar → Visual Timing
演示视觉怎样知道“什么时候发生”。

链 2 · CONTROL

MIDI / Keyboard → Router → Parameter / Action
演示一个真实控制器消息怎样进入系统。

链 3 · STATE

State → Layers / Parameters → Output
演示切一次 State 时多条关系怎样一起变化。

最后 · RECOVERY

Esc / Panic / Reset → Stable State
让大家看到系统怎样回到一个可继续工作的起点。

给讲者：这一段讲到哪里
  • 先隐藏不需要的调试面板，避免大家被代码量吓到。
  • 每条链只演示一个例子，现场把鼠标或控制器动作做得明显。
  • 如果某个技术环节现场失效，回到网页图示继续讲；不要为了修设备消耗整段课程。
这一节的结束条件：听众面对一个陌生实时工程时，知道应该先找 Clock、Control、State、Output，而不是试图一次读完所有代码。
