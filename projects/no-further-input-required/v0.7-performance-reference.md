# No Further Input Required v0.7 — Performance System Reference

> Snapshot record / reusable design reference / 2026-08-22

## Why this version is worth preserving

v0.7 is not yet the final gallery form of **No Further Input Required**, but its **performance framework is valuable and reusable**. It establishes a browser-based audiovisual instrument that can keep playing by itself while still allowing direct live intervention.

The version should therefore be treated as a **reference implementation for future Live Set / web instrument projects**, not as disposable WIP.

## What v0.7 gets right

### 1. Continuous musical ground

The background music does not stop when the visual state changes. This gives the whole instrument one continuous temporal field instead of six isolated demos.

This is the main structural success of v0.7:

```text
continuous generative music
        ↓
shared clock / BPM / bars
        ↓
multiple visual behaviours
        ↓
live triggers + autonomous progression
```

The music acts as the common substrate; visual states are different behaviours performed inside the same timeline.

### 2. Autonomous + playable at the same time

The system can continue without constant input (`AUTO`) but can still be interrupted or redirected by a performer (`NEXT`, `HOLD`, keyboard, pointer/touch).

This hybrid mode is important for future instruments:

- the system should never feel dead when the performer stops touching it;
- performer input should modify or intensify an already-running process;
- live control should be sparse but consequential;
- automatic behaviour and manual behaviour should share the same clock rather than behave like two separate applications.

### 3. Multiple visual states sharing one instrument

`ROUTE / FIELD / ORBIT / REWIND / CELLS / PARTITION` prove that a browser instrument can contain several distinct visual grammars while retaining one common musical identity.

The valuable idea is **not the six states themselves**. The reusable idea is:

> one performance runtime can host several visual behaviours while music, timing, input and global transport remain persistent.

### 4. Keyboard as an alternate performance surface

The 1–0 / A–Z mapping is useful as a performance fallback and as a way to quantize direct triggers. It should not be treated as the only or primary interaction model.

For future touch-first instruments, keyboard input can remain as:

- desktop fallback;
- rehearsal shortcut;
- MIDI/QWERTY bridge;
- discrete trigger layer on top of continuous pointer gestures.

### 5. Browser as instrument, not page

The strongest reusable principle is that the webpage behaves like an audiovisual instrument rather than a website with buttons.

Future projects should inherit this attitude:

- fullscreen-first;
- minimal UI;
- sound is part of the runtime, not an optional decoration;
- interaction should immediately affect both visual and sonic behaviour;
- the system should be performable for several minutes without navigating menus.

## What should NOT be inherited blindly

### A. Pointer-following clutter

Some current states (especially the mouse-following / orbit-like behaviour) react too literally to the cursor. Objects chasing the mouse produce visual noise and make the performer feel like they are dragging UI elements rather than playing a system.

Avoid:

```text
pointer position → object position
```

Prefer:

```text
pointer gesture
   ↓
velocity / curvature / loop / crossing / dwell
   ↓
spawn / excite / rotate / quantize / mutate
   ↓
system continues after the pointer leaves
```

The pointer should **inject energy or structure**, not become a leash attached to graphics.

### B. State switching as the dominant event

The current six-state framework works for performance experiments, but switching between complete visual scenes can feel like preset browsing.

Future live instruments should increasingly allow:

- behaviours to overlap;
- one gesture to activate a local process inside the current field;
- previous events to leave residues;
- multiple modules to coexist at different densities;
- transition to happen through accumulation / suppression rather than hard scene replacement.

### C. Visual response is sometimes too generic

A trigger should not merely cause “something to move.” It should create a legible behaviour with a beginning, development and release.

A useful event envelope is:

```text
trigger
→ attack
→ development
→ transformation
→ decay / residue
```

This is the part to combine with the interaction grammar of touch-oriented audiovisual instruments.

# Performance direction to reuse in other instruments

## Reference interaction model

The desired direction combines three ideas:

1. **v0.7** — continuous autonomous music + multiple behaviours + sparse intervention;
2. **touch:waves-like grammar** — one input invokes a coherent audiovisual behaviour, not only a parameter change;
3. **Playground-like touch composition** — pointer/touch gestures can place, drag, repeat, cross and retrace shapes inside a spatial field.

The important interaction shift is:

```text
CLICK / KEY
    ↓
discrete event
```

becoming

```text
GESTURE PATH
    ↓
shape + velocity + repetition + crossing
    ↓
audiovisual phrase
```

Examples:

- draw a figure-eight repeatedly → a phrase becomes denser / more syncopated;
- place a moving element inside a region → that region becomes an active musical cell;
- circle an existing element → excite / duplicate / harmonize it;
- cross two trajectories → generate a collision event;
- hold still → freeze / sustain / accumulate;
- erase through a region → suppress or mute behaviours;
- release the pointer → the created structure keeps running instead of disappearing immediately.

## Performance principle

> The performer should manipulate **behaviours and trajectories**, not drag graphical objects around.

This principle should be reused across future Live Set instruments.

# Recommended reusable architecture

```text
Transport / BPM / Bars
        │
        ├── Generative Music Engine
        │
        ├── Autonomous Event Scheduler
        │
        └── Input Interpreter
                 │
        ┌────────┼────────┐
        │        │        │
      keys     touch    pointer
        │        │        │
        └──── gesture semantics ────┐
                                    ↓
                            Behaviour Modules
                                    │
                 ┌──────────────────┼──────────────────┐
                 │                  │                  │
              visual             audio             residue
                 │                  │                  │
                 └──────────────────┴──────────────────┘
                                    ↓
                            Shared World State
```

## Gesture features worth extracting

An agent implementing future instruments should derive at least:

- `position`
- `velocity`
- `acceleration`
- `direction`
- `curvature`
- `pathLength`
- `loopDetected`
- `crossingCount`
- `dwellTime`
- `gestureEnergy`
- `repetitionRate`

Do not map all of them directly to visual parameters. Use them to select or modulate **behaviours**.

# Reuse policy

When another project asks to “use the NFI v0.7 performance framework”, inherit:

- continuous generative musical background;
- one global transport / BPM clock;
- autonomous playback;
- sparse manual intervention;
- keyboard fallback;
- touch / pointer as performance input;
- multiple visual behaviours in one runtime;
- event envelopes with attack / development / decay;
- persistent residue after gestures;
- minimal fullscreen UI.

Do not automatically inherit:

- current visual aesthetics;
- current six state names;
- literal cursor-following objects;
- hard state cuts;
- every key mapping;
- current canvas implementation details if a newer renderer is more suitable.
