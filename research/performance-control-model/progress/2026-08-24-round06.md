## ACTIVE RESEARCH TASK

Improve the unified sequencer without adding more conceptual layers.

The focus is now **live editability, explicit randomness and low-error control states**.

## USER FEEDBACK

The unified table is directionally correct because it supports precise preparation while keeping live input compressed.

The previous implementation still failed in three practical ways:

1. the grid was not comfortable to edit while transport was running;
2. randomisation was not exposed as an explicit, isolated action;
3. preset switching/evolution was not clear enough, and the control buttons overlapped semantically.

## D5 v4 — LIVE EDIT SEQUENCER

### Stable live-edit grid

The matrix DOM is now created once and kept stable during playback.

The transport only moves a playhead class across existing cells.

This means a performer can click cells while the sequence is running without the target node being replaced every step.

Each lane cell is always:

```text
OFF → WEAK → STRONG → OFF
```

### Simplified top-level controls

```text
PLAY / STOP
RANDOM LANE
RANDOM ALL
STEPS 8 / 12 / 15 / 16 / 20
AUTO BARS 1 / 2 / 4 / 8
CLEAR ALL
```

`PLAY / STOP` controls transport only.

No START/RESET ambiguity remains.

### Lane controls

Each lane exposes only:

```text
TRIGGER
LATCH
```

Keyboard remains:

```text
A S D F J K L ;       → one cycle
Shift + key           → toggle latch
```

### Preset model reduced to four slots

Each lane has four stored pattern rows:

```text
P1 P2 P3 P4
```

Preset slots are not separate sequencers.

They only store/recall the visible row for that lane.

Editing the grid writes back to the active preset automatically, so there is no SAVE button and no unsaved-edit state.

### Explicit automatic preset behaviour

Only three modes exist:

```text
HOLD
CYCLE
RANDOM
```

They apply only to latched lanes.

`AUTO BARS` defines when the preset changes.

This separates two different ideas clearly:

```text
RANDOM LANE / RANDOM ALL
= generate new event arrangements now

AUTO RANDOM
= recall a random stored preset later on a bar boundary
```

## CONTROL PRINCIPLE

The live system should minimise ambiguous control states.

A control should answer one question only:

```text
PLAY      → is transport running?
TRIGGER   → play this lane once?
LATCH     → keep this lane running?
RANDOM    → generate a new pattern now?
AUTO MODE → should latched presets change over time?
```

This keeps the internal system precise while reducing front-stage mistakes.
