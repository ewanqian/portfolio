# 新媒体工程控制论
## New Media Engineering Control Model

这是一份面向新媒体艺术创作者、实时影像表演者、声音艺术家、Creative Coder 与工作坊参与者的公开讲义。

它借用控制论、交互系统与工程设计中的一些基本概念，回答一个很实际的问题：

> **为什么很多新媒体 Demo 很快就会变成“按一下出一个效果”，而一个真正可以被观看、被演奏、被长期维护的系统，需要多出哪些结构？**

这里的“新媒体工程控制论”是一个**实践框架**，不是一个已经被学术界确立的独立理论名称，也不是对经典控制论的替代。它的作用，是把抽象概念翻译成创作者可以直接用于作品设计、排练、测试和迭代的问题。

---

# 一分钟版本

一个实时作品可以先被看成一个不断循环的系统：

```text
现在系统是什么状态
+
人刚刚做了什么
+
现场发生了什么
↓
系统进入下一个状态
↓
声音 / 视觉 / 灯光 / 空间产生结果
↓
人听见、看见、感受到结果
↓
再做下一次判断
```

如果用一个控制论式的表达，可以写成：

```text
x(t+1) = F(x(t), u(t), d(t))
```

把它翻译成人话：

> **下一刻的系统，不只由“你刚按了什么”决定，还由“它现在在哪里、之前发生过什么、现场条件是什么”共同决定。**

其中：

- `x`：系统当前状态；
- `u`：人的操作；
- `d`：现场扰动或外部条件；
- `F`：系统规则。

真正重要的变化是：

> 不要只问“这个按钮触发什么？”  
> 先问“系统现在在哪里，我这个动作准备把它带到哪里？”

---

# 1｜从“效果”转向“系统”

最简单的新媒体原型常常是：

```text
A → 一个声音 + 一个圆
B → 一个声音 + 一条线
C → 一组粒子
```

这种 Mapping 完全合理，而且非常适合快速验证。

问题是，如果结果几乎只由当前输入决定：

```text
Result = Input
```

那么第一次按 A 和一分钟以后按 A，本质上没有区别。

一个更深的实时系统通常更接近：

```text
Result = Input + State + History
```

同一个输入，在不同状态中拥有不同意义：

```text
A 在 OPEN
→ 只留下一个稀疏 pulse

A 在 BUILD
→ 增加 subdivision 与 movement

A 在 PEAK
→ 成为强 accent

A 在 BREAK
→ 不再增加，而是留下 tail 或帮助抽离
```

按钮没有变多，系统却变深了。

这就是从“效果集合”走向“可控制系统”的第一步。

---

# 2｜State：系统现在在哪里

实时作品不一定需要很多参数，但需要一些真正影响后续结果的状态。

例如：

```text
SECTION
ENERGY
TENSION
DENSITY
SPACE
MEMORY
ACTIVE AUDIO LAYERS
ACTIVE VISUAL LAYERS
TIME / BAR / PHRASE
```

一组可能的状态：

```text
SECTION = BUILD
ENERGY = 0.62
TENSION = 0.81
DENSITY = 0.48
SPACE = 0.55
```

此时用户按下 `HOLD`。

`HOLD` 不需要只等于“把一个音拉长”。

它可以代表：

> **暂时维持这个结构，不进入下一次释放。**

于是不同媒介分别解释同一个决定：

```text
MUSIC
保持 tension，不把完整低频放出来

VISUAL
减少新对象，让已有结构继续积累

LIGHT
保持空间狭窄，不完全打开
```

这就是 Shared State。

声音、视觉与灯光不必做同一件事，但它们知道“现在是什么状态”。

---

# 3｜Feedback：为什么实时作品是一个回路

固定成片更接近：

```text
时间轴
↓
播放
↓
结束
```

这是一个相对开放的单向流程。

实时表演更接近：

```text
人做判断
↓
系统产生结果
↓
人听 / 看结果
↓
重新判断
↓
再次介入
```

这就是反馈回路。

反馈的价值不是“让一切都实时变化”，而是让作品可以根据刚刚发生的结果继续被修正。

因此，创作者需要设计的不只是输入，还包括：

- 我怎么知道系统现在发生了什么？
- 我怎么判断下一步？
- 我的动作什么时候真正生效？
- 如果判断错误，我怎么回来？

---

# 4｜Stability：系统不能只会越来越多

很多 generative system 的默认方向是：

```text
ADD
ADD
ADD
ADD
ADD
```

最后声音越来越响、视觉越来越满、灯光越来越亮。

这不是丰富，而是失控。

稳定性不等于“永远不变化”。

更实用的定义是：

> **无论系统怎么变化，它仍然有办法回到可以继续工作的范围。**

因此系统应该拥有边界：

```text
MAX AUDIO VOICES
MAX VISUAL DENSITY
MAX LIGHT INTENSITY
LIMITER
AUTO DECAY
PRIORITY
RESET / PANIC
```

这些限制不是在削弱创作，而是在把容易出事故的复杂度交给系统处理。

---

# 5｜Controllability：不仅要会进入，还要会退出

一个系统如果只有“增加”，通常很难被长期演奏。

真正的控制至少需要成对关系：

```text
ENTER / EXIT
ADD / REMOVE
BUILD / RELEASE
ACCUMULATE / CLEAR
RECALL / FORGET
OPEN / CLOSE
```

一个非常简单的测试是：

> **现在已经很满了，我能不能在 8 或 16 bars 内主动让它回到很空？**

如果做不到，再多效果也不等于可控。

---

# 6｜Observability：演奏者不能失明

观众可以只看到作品，但操作者需要知道系统正在做什么。

至少要能判断：

```text
当前 Section
当前 Energy / Density
哪些 Layer 正在运行
有没有 Pending Transition
下一次 musical boundary 在哪里
Reset 是否可用
```

因此最好区分：

```text
PERFORMER UI
≠
AUDIENCE VISUAL
```

观众看到的是作品。

表演者看到的是控制信息。

这也解释了为什么一个漂亮的全屏画面，不一定是一个好用的演出界面。

---

# 7｜Robustness：不要求人永远按得完美

如果系统只有作者本人、在某一台电脑、精准按在某一拍才能成立，它很难进入公众工作坊、展览或真实舞台。

一个更稳健的系统应该容忍：

- 早一点按；
- 晚一点按；
- 少按几次；
- 换一个操作者；
- 输入材料改变；
- 一部分效果失败；
- 帧率下降或网络有延迟。

Quantization 是最常见的保护方法之一。

例如用户在第 15.72 bar 请求：

```text
PEAK
```

系统先记录：

```text
pending = PEAK
```

到第 16 bar 再正式执行。

于是：

```text
人负责：我要 Peak。
机器负责：什么时候落下去最可靠。
```

这是一种非常重要的人机分工。

# 8｜不同媒介，不需要同速运动

共享状态不等于所有媒介必须每拍同步。

## Music

音乐适合处理：

- rhythm；
- anticipation；
- withholding；
- build；
- drop；
- release。

它可以在 1/16、beat、bar、phrase 上快速变化。

## Visual

视觉适合处理：

- persistence；
- accumulation；
- transformation；
- occlusion；
- memory；
- return。

一个视觉结构可以持续几十秒甚至跨越多个段落。

## Light / Space

灯光与空间适合处理：

- reveal；
- hide；
- isolate；
- narrow；
- expand；
- blackout；
- open the room。

因此同一个 `PEAK` 可以表现为：

```text
Music：增加身体能量
Visual：反而删掉大量细节，只留下一个主结构
Light：突然打开整个空间
```

它们没有复制彼此，却共同解释同一个状态。

这是一种更成熟的“同源”。

# 9｜Hierarchical Control：从一个按钮到一场大型演出

大型演出不能由一个控制层管理全部时间尺度。

可以把控制层级拆成：

```text
SHOW
↓
SET
↓
TRACK / PIECE
↓
SECTION
↓
PHRASE
↓
CELL / CAPSULE
↓
EVENT
```

## Event

一个 kick、一次 flash、一个音符。

## Cell / Capsule

一个能自己成立 1–8 秒的小行为。

## Phrase

几个 Cell 组成的时间关系。

## Section

OPEN、BUILD、PEAK、BREAK 这类更长的状态。

## Track / Piece

一首完整的演出单元。

## Set

多个 Track 与转场。

## Show

音乐、视觉、灯光、舞台、表演者与观众共同组成的整体。

这解释了一个重要问题：

> **网页小乐器和大型现场并不是完全不同的世界。差别首先是控制层级、内容完成度和制作尺度。**

# 10｜用“演出剧本”控制 Macro Structure

对于第一次做实时系统的人，不需要先写复杂乐谱。

可以先用五段结构：

```text
OPEN
↓
BUILD
↓
PEAK
↓
BRIDGE / BREAK
↓
RETURN / END
```

每一段只需要回答四个问题：

1. 当前能量多高？
2. 当前密度多高？
3. 谁是主角？
4. 下一段怎样进入？

例如：

| Section | Music | Visual | Control |
|---|---|---|---|
| OPEN | 稀疏、长 decay | 大负空间 | 少操作 |
| BUILD | subdivision、累积 | 重复、分裂、推进 | ADD / HOLD |
| PEAK | 完整低频与节奏 | 强 foreground | 选择主行为 |
| BREAK | 抽离主脉冲 | 空场、残留、延迟 | REMOVE / RELEASE |
| RETURN | 更少的材料 | 召回或收束 | END / RECALL |

演出结构的价值不在于套公式，而在于帮助观众感受到方向。

# 11｜Hybrid Control：预制、自动与人工判断之间

完全写死的时间轴很稳定，但现场判断空间有限。

完全开放的随机系统很自由，但容易失控。

更适合很多新媒体现场的方式是：

```text
预先设计并试听过的可靠材料
+
系统自动维持时间与安全边界
+
人在少数关键位置做结构决定
```

可以称为：

**Hybrid Control / Controlled Improvisation**

系统可以负责：

```text
BPM
CLOCK
QUANTIZATION
PITCH COMPATIBILITY
MAX VOICES
GAIN SAFETY
DENSITY BUDGET
TRANSITION SCHEDULING
RESET
```

人负责：

```text
现在进入吗？
还要继续等待吗？
应该加还是减？
要让什么留下？
旧东西现在该回来吗？
现在应该释放了吗？
```

机器处理精确、重复和风险。

人处理意义、方向和判断。

# 12｜把工程流程也看成一个控制回路

“控制”不仅存在于演出现场，也存在于创作过程本身。

一个有效的制作循环可以写成：

```text
FRAME
先确定作品怎样工作
↓
FILL
加入材料
↓
FINISH
测试、删减、修正
↓
FEEDBACK
让别人使用 / 观看
↓
NEXT VERSION
```

AI Coding、Creative Coding、游戏引擎、Three.js、Tone.js、MIDI、OSC 都只是实现层。

真正决定项目能否推进的是：

- 当前版本解决什么问题；
- 当前系统有哪些状态；
- 哪些东西应该被系统保护；
- 哪些判断必须留给人；
- 失败以后能不能回退；
- 测试结果如何改变下一版。

换句话说：

> **一个好的创作工作流，本身也是一个有反馈、有边界、有状态的系统。**

---

# 13｜四个最实用的验收问题

任何实时系统都可以先问：

```text
1. 现在是什么状态？
2. 我这个动作改变了什么？
3. 我停手以后会发生什么？
4. 我怎么把它收回来？
```

再加四个测试：

## 30 秒无输入测试

停手以后，系统是不是马上死掉？

## 返回测试

已经很满时，能不能主动回到更空的状态？

## 新手测试

只说明 2 分钟，一个不熟悉系统的人能不能完成一次 build → release？

## 观众测试

只给别人看 Screen + Sound，不解释控制方式。

他们看到的是：

> 一段作品 / 演出？

还是：

> 有人在测试一个网页？

---

# 14｜这个框架不要求所有作品都变成“乐器”

控制模型不是为了让每件新媒体作品都拥有键盘、BPM 或现场表演。

不同作品可以有不同控制关系：

- 互动装置可能把观众位置当作输入；
- 展览影像可能只保留非常少的人为控制；
- 生成影像可能让系统长期自主运行；
- 多屏空间可能把灯光、影像和声音写进同一个 Show State；
- AI 系统可能把人的选择、生成结果和下一次生成组成反馈回路。

真正通用的问题仍然是：

> **状态是什么？输入是什么？系统如何变化？人如何知道结果？失控以后怎么回来？**

---

# 15｜一句话总结

> **新媒体工程控制论不是教你控制更多参数，而是帮助你设计：什么应该自动，什么应该由人判断；什么可以变化，什么必须被保护；一个动作怎样进入时间、状态和反馈，最后形成可以持续工作的作品。**

这套框架最适合在真正的原型、排练、展览和现场测试中继续修正，而不是停留在概念层。
