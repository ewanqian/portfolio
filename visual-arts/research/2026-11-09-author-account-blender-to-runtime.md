## 一条真正的研究线

对我而言，从 TIMER 到 Drop Flow，再到 KASHIWA 的不同音乐视觉、NFIR、SRE 与 Entropy，真正值得留存的并不是一些通用的抽象几何风格，而是**我怎么从传统的 Blender 场景与时间线，进入 Simulation Zone 的逐帧状态演化；又怎么尝试将已烘焙的音频控制、手动关键帧、镜头选择与实时外部输入重新转换成可执行的程序**。

长远目标是从原始 Blender 工程中翻译出一套可直接调用本地 GPU 的 runtime，并在需要时接入 TouchDesigner 或其他系统。重新写出一个“看上去像”的粒子流而丢失原作的生成方式，不算真正继承。

## 1. TIMER / 控时者：从俯拍场景到屏幕反求

在作者对早期 TIMER 工作方式的回忆中，它首先是一个复杂的 Blender 视觉动画工程，但主要仍以传统场景构成、时间线和手动编排为基础。原始构图是**俯拍的正方形时钟构图**；其中组合了圆形、视频纹理、预先烘焙的图像、黑白化、ColorRamp 等视觉处理。它并不是一个从头到尾由 Simulation Zone 驱动的作品，也不需要把它解释成“时间哲学”的程序。

对作者而言更值得回看的两个部分：

1. **图像转译 / 反求**：有一份独立工程尝试将俯视的正方形构图中的圆形关系通过空间和透视关系“掰开”，再以近大远小等方式对应到一条特别长的横向屏幕规格。必须找到实际 Blender 对象、相机和参数，不能把“反求”误写成简单裁切或球体映射。
2. **音频与动画控制**：辨认哪些动画使用已经 Bake 到 F-Curve/关键帧上的音频曲线，哪些是作者手 K，哪些是视频纹理或普通时间线动画。它们未来应能被分别替换为离线曲线、实时音频包络、BPM 事件或现场人工输入。

作者并不认为 TIMER 必须被完整重新创作；重点是发现它已有的技术经验和可复用的动画控制方法。

## 2. TIMER → 平面 Drop Flow：二维流动的起点

作者回忆：在 TIMER 转译到长条屏幕的平面画面后，曾经叠加一种**从左到右不断流动的点**。这是 Drop Flow 二维化的早期原点，也是开始尝试 Geometry Nodes **Simulation Zone** 的重要阶段。

这条过渡线需要在实际文件中查证，不应把后来成熟的三维 Drop Flow 直接投射回这个早期二维状态。

## 3. Drop Flow / 滴流：从时间线进入逐帧模拟

到了 Drop Flow，作者开始尝试把此前平面的效果三维化。核心变化是：不只是安排一次性画面，而是在 Simulation Zone 中让**每一帧都生成、保留、更新、筛选和删除**一批状态。作者用 Processing 的 setup / draw 作类比：早期时间线更像安排好初始内容和事件；Drop Flow 更接近持续更新的 draw 循环。

真正值得研究的问题：

- 模拟区每一帧具体如何生成或复制几何；“一秒很多次”究竟是每帧多个发射体、多个样本、重复节点、子帧还是实际迭代，必须从节点和 FPS 验证，不能按形容词猜测。
- 哪些属性在相邻帧之间保留；哪些是每帧重新计算；哪些使用时间/随机、噪声、波形和生命周期门控。
- 能否把速度、加速度、快进慢出和自定义运动曲线纳入逐帧模拟，而不是只能被动响应已经烘焙的音乐强度。
- 当年的创作中，作者实际上**很难精确控制系统**：很多参数跟随音乐强度，人工能做的往往是改变角度、挑选片段与观察生成结果。这是实际限制，不能在后述中改写为“完善的实时演奏系统”。

作者对过去的 Processing 或 openFrameworks 复现有清楚的不满意：很多结果只是外观相近，运动、密度和生成关系却“不对，没有那个味儿”。因此 GPU 移植首先要做机制等价与视觉对照，再谈性能优化。

## 4. KASHIWA Daisuke：同一生成系统，不同音乐审美

2025 年与柏大辅 KASHIWA Daisuke 相关的一批视觉并非各自独立从零生成。作者复用了、复制并修改 Drop Flow 的工程，在多次工作及日常练习中形成新的视觉分支。

值得保留的作者侧审美判断：

- **Amb**：比较浪漫、流动的情绪；不是以每拍猛烈冲击为唯一目标。
- **Ice**：作者特别惊喜的是它与音乐节拍的准确贴合；整体音乐的强张力使基于音乐信号的检测也能产生出色的卡点效果。具体检测方式、曲线和节点仍待工程查证。
- **White Night / Whitenight、Lead 等**：属于需要逐版本核对的分支，不能将一套工程的控制机制、画面特征一概转述到全部曲目。
- **创作方法**：同一组底层规则被多次复制、变形、比较后，才发展出不同视觉情绪。这种批量分化后再做作者选择的方法应进入创作偏好档案。

视频证据入口：[KASHIWA 系列总档案](../kashiwa-daisuke/README.md)，包括 Lead、Whitenight、Amb、Titan、Phantom、Ice 的外链。具体文件与曲目对应关系需本地核对。

## 5. NFIR / 无需进一步输入：从复杂音乐系统到简化的自主生成与观看

相对于 Drop Flow 的音乐依赖和难以控制，NFIR 刻意变得更干净、更简单。一部分是程序按规则持续运行和生成，变化本身并不丰富；另一部分是作者**主动操作 Blender 并录制屏幕**：调整形状的边数（如三角、六边乃至更多边）、角度、观察方向与几何重合关系，由此获得细腻或强烈的瞬间。

这两部分必须分别归档：

- **System-running**：不依赖不断输入的原始生成状态。
- **Human-observing / Human-operating**：作者改变参数、视角并录屏的时间过程；甚至鼠标本身也可能保留在记录中。

作品的重要张力不是“它拥有多么复杂的自主 AI”，而是**正常运行的过程，与人有意识地观察和操作时产生的画面之间的差异**。作者知道很多极佳瞬间只留在自己的记忆或录屏里，最后公开的固定结果反而可能显得无聊。今后 Agent 可以帮助系统化回找、筛选和回放这些片段，但不能替代作者判断。

请优先找到 NFIR 原始版本、NFIR3 以及 FINAL_LOOP 等派生版，区分后期添加的编排和最初机制。

## 6. Drop Flow × Motion Capture：尚未完成的实验

这是**未完成的研究线**，不是已经交付的作品。作者回忆在双年展相关工作中已有舞者动作数据，曾考虑将 Drop Flow 的流动系统与人体运动关联：不仅把身体当作粒子发射器，还可以**复制不同时间的舞蹈姿态和动作片段**，探索机器人/AI 对姿态、时序、镜头、角度和数据标注的编排。

一个重要构想是把视觉烘焙成 360° VR 影像，让舞者戴上头显去感知身体与生成图像的关系；音乐结构可能产生类似多米诺骨牌的连锁推动。以上是作者描述的**研究提案与记忆**，必须通过实际素材确定：已有动作数据是什么、权利如何、是否已制作 VR 版本、是否已有任何可运行原型。

## 7. SRE / BPM Link Experiment（2026）：大量候选与即时筛选

作者转向实时工程的重要经验来自 2026 UFO Terminal「加载…创作营」语境中的 SRE 合作。Mark、RÖ 和作者各自负责不同的声音/信号/视觉部分；RÖ 的节拍相关设备与 MIDI/BPM 输入，使 Processing 的实时视觉可以被音乐信息驱动。

作者回忆：曾在一晚内让 Agent/Codex 大量生成 Processing 视觉，约十组、组内各有多种状态，观察后保留若干组和二三十个较满意的状态。这一说法与旧档案“约十套原型、最后选中约四组方向”可能是**不同统计粒度**（组与组内状态）；不要在未核对视频与程序前当作矛盾或单一精确数字。

这是第一次强烈感受到快速并行原型的创作优势：以往大型屏幕项目要花很多时间等待模拟、输出、试映与现场往返；大量低分辨率候选可在短时间内供作者挑选方向。这个效率革命解决的是**可见性与选择空间**，未必自动解决复杂动态或成熟的视觉编排。

作者偏好的画面包括大尺度数据终端、航站楼式信息构成、点线面与文字共同组成的复杂场景；同时反思早期生成结果可能显得较静态，只提供了期待感。

该项目已有正式档案：[BPM Link Experiment](../../projects/bpm-link-experiment-2026.md)、[SRE Realtime Lab](../../archive/sre-lab/README.md)；不要另建同名正式作品。

**新找到的一手公开影像来源**：[MANA｜BPM Link Experiment SRE 主机位正式视频](https://www.manamana.net/video/detail?id=3001136)，页面标注发布日期 2026-08-18，并展示完整说明与三人 credit；这一发现证明线上已有对应的公开视频页，但**尚未验证网页播放是否正常，也不代表本地原始视频已入 GitHub**。

## 8. Entropy / Atmospheric Escape（2026）：跨屏终端与太空行程

作者希望打造类似电脑操作终端的太空旅程：由地球出发，向月球和外太空推进。制作中进一步继承 SRE 的快速原型与实时控制经验，也加入 3D 模型、状态切换动画、星空与航天器观察、跨屏幕图像编排，让画面接近信息系统或沙盘的体验。

作者回忆可能有**两组星空内容、三种航天器观察版本**，需要与实际文件、节目录像逐项核对，暂不能写成正式交付数量。

作者同时保留明确的未竟目标：更加繁密、复杂、精确的点、线、面、文字与空间关系，具有类似 Ryoichi Kurokawa 作品中信息密度和视觉组织的精细程度。当前 AI 批量原型并没有自然实现这一点。

本仓库的 [Entropy Post-show Closeout](../../works/entropy-0905-performance/POST-SHOW-CLOSEOUT.md) 已明确区分实际使用、测试未使用与计划未完成。这里保留作者的创作意图，不以制作计划代替现场事实。

## 当前面向未来的研究问题

1. 从 Blender 工程中读出真实的音频 Bake 曲线、手 K、视频纹理、相机变化和 Simulation Zone 状态。
2. 把音频曲线作为可交换的**控制数据**：离线回放、实时音频分析、BPM/MIDI、人工手势/OSC 均可驱动同一机制。
3. 将 Drop Flow 的核心模拟从 Blender 节点图转换为由本地显卡计算的原生实时引擎；做到**机制正确、视觉接近、计算效率高**，而不是换一种流体特效。
4. 按真实来源和版本把可复用的视觉资产与控制行为整理进可检索库；记录哪些已完成、哪些只是尝试、哪些被放弃或仍显粗糙。
5. 为 Writing 专栏形成一篇关于「从 TIMER 的平面转译到 Drop Flow 的状态模拟，再到原生实时视觉」的研究文章；待工程核对和作者校稿后再发布。

## 事实与核验边界

- 以上创作动机、作品内部体验和偏好来自作者本人 2026-11-09 的后期口述，属于宝贵的一手证词，但**不是 Blender 源文件技术数据**。
- 所有节点连接、FPS、发射次数、Bake 属性、版本与渲染结果需本地 Codex 实查。
- TIMER 与 Drop Flow 原属团队/协作语境；作者的个人创作体验不自动覆盖完整 credits。
- NFIR 的“自主”仅指简化规则后持续运行，不自动意味着智能决策或复杂的自组织行为。
- Motion Capture、360° VR、GPU Runtime 属于研发/未完事项，除非有可运行证据不得写成完成作品。
- 本文是供人审的研究档案，不自动进入 CV、精选作品、首页或正式 Writing。
