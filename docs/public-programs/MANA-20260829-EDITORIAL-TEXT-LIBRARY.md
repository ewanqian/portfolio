# 2｜这是什么工作坊？

很多数字创作课程从软件开始：先理解界面、节点、参数和插件，最后再尝试把这些功能组合成一件作品。

这次工作坊把顺序反过来。

我们先问：

- 你希望别人做什么动作？
- 这个动作应该产生什么声音？
- 画面为什么在这一刻变化？
- 一个输入能不能同时影响多个结果？
- 系统什么时候应该安静，什么时候应该进入高能状态？

软件只是实现这些关系的工具。

工作坊会使用网页、Creative Coding 与 AI 辅助编程，尽量跳过冗长的软件熟悉过程，让参与者直接进入一件实时作品最重要的结构：**Input、Mapping、State、Feedback 与 Performance。**

### 图形化说明建议

常见的软件学习路径：

```text

```

```text
↓
规则 / Mapping
↙          ↘
声音         图像
↘          ↙
State / Feedback
↓

```

# 3｜什么是“音画同源”？

“音画同源”不是一个需要读者预先掌握的学术门类，而是我们在这次工作坊里用来描述一种创作关系的工作概念：

**声音和视觉不只是前后配合，而是尽可能从同一个动作、参数、数据或规则中共同产生。**

最简单的例子是：

- 按一次键，同时触发声音与动画；
- 鼠标移动，同时改变滤波与图像尺度；
- 一个推子，同时改变声音密度与画面残影；
- 一个按钮，让系统从 Quiet State 切换到 Active State。

传统的“音频驱动视觉”通常是：

```text
声音已经产生
↓
分析音量 / 频率 / 节拍
↓
视觉跟随变化
```

而“同源控制”更接近：

```text
Gesture / Input / Data
        ↓
      Mapping
      ↙     ↘
   Sound   Visual
```

声音与视觉都是系统的结果，真正被设计的是它们背后的关系。

这个概念也对应数字乐器设计中的一个核心问题：一个控制动作与系统参数之间如何 Mapping，会直接影响这件数字乐器是否容易理解、是否值得练习，以及能否形成自己的表演语言。

# 4｜三个最适合普通读者的案例

## 4.1 Patatap｜网页为什么可以是一件乐器？

**Patatap** 是 Jono Brandel 与 Lullatone 合作的网页视听乐器。用户只需要敲击键盘，A–Z 与空格就会触发对应的声音和动态图形。

它的结构并不复杂，核心甚至是非常直接的一对一 Mapping，但丰富的声音组、动画与即时反馈让用户很快获得“正在演奏”的感觉。

Patatap 最适合作为这次工作坊的第一个案例，因为它把一个抽象问题说得非常直白：

> **一个网页不一定只是网页，它也可以像鼓机、键盘或玩具一样成为一件乐器。**

## 4.2 touch:waves｜一块触摸屏如何成为视觉乐器？

**touch:waves（2021–）** 由 sascacci + ksmt 创作，是一件可以直接在显示屏上触摸演奏的 visual instrument。

作品将屏幕划分为多个区域，每个区域映射不同的声音与声音对应的视觉形态；用户触摸并移动手指时，声音和视觉会一起发生变化。

它特别适合解释本工作坊的第二层目标：

> 不只是“按一下出现一个效果”，而是开始设计一套可以持续操作、具有空间和连续变化的演奏界面。

## 4.3 Golan Levin / AVES｜声音和视觉能不能被当成同一种“材料”？

Golan Levin 在 MIT Media Lab 发展的 **Audiovisual Environment Suite（AVES，1998–2000）** 是一组实时视听系统。它允许使用者通过手势，在同一个界面中实时生成抽象动画与合成声音。

AVES 使用“audiovisual substance / 视听物质”作为界面隐喻：与其把声音和画面理解成两个最后再拼起来的文件，不如把它们理解成同一种动态材料的两个维度。

这和我们的工作坊非常接近：参与者真正设计的不是“音频文件 + 视频文件”，而是一套动作、参数、声音和视觉之间的关系。

资料 / 图片 / 视频参考：
- MIT Media Lab / AVES：https://acg.media.mit.edu/people/golan/aves/
- Golan Levin 项目档案：https://www.flong.com/archive/projects/aves/index.html
- Scribble Live Audiovisual Concert：https://acg.media.mit.edu/people/golan/scribble/

## 5.1 Michel Waisvisz / The Hands｜让数字控制重新回到身体

荷兰电子音乐家 Michel Waisvisz 长期探索电子乐器与身体动作之间的关系。他开发的 **The Hands** 是数字音乐史中重要的手势控制器案例：通过佩戴在手上的传感控制器，演奏者的身体动作成为电子声音系统的一部分。

这个案例适合解释：数字乐器并不一定要复制钢琴或吉他；新的控制方式本身也可以形成新的演奏身体和表演语言。

## 5.2 Ei Wada / ELECTRONICOS FANTASTICOS!｜废弃家电也可以重新成为乐器

日本艺术家 **Ei Wada（和田永）** 发起的 **ELECTRONICOS FANTASTICOS!** 从 2015 年开始，与不同背景的参与者合作，把废弃 CRT 电视、电风扇、摄像机、电话等家电重新改造成电磁乐器，并逐步形成共同演奏的乐团与参与式艺术项目。

它提醒我们：所谓“新乐器”并不等于更昂贵、更先进的设备。真正重要的是重新设计物体、身体、声音与控制之间的关系。

## 5.3 Ryoji Ikeda / datamatics｜数据同时成为声音与视觉的材料

Ryoji Ikeda 的 **datamatics** 系列直接把“pure data / 纯数据”作为声音与视觉的共同来源。官方项目说明中，作品会从硬盘错误、软件代码等数据结构出发，将数据以声音和动态图像的方式同时物质化。

这个案例适合把“音画同源”从乐器扩大到更广的系统创作：共同源头不一定是一个按键，它也可以是一组数据、一段算法或一种实时计算过程。

# 6｜Mapping：为什么“一个按键”值得讲？

一个按键看起来只有 0 和 1，但数字系统可以把它扩展成非常丰富的行为：

- 按下：触发声音与图像；
- 按住：进入持续状态；
- 连续快速按：根据速度增加密度；
- 两次按键之间的间隔：成为新的连续参数；
- 同一个按键：同时控制多个声音与视觉参数；
- 触发之后：让系统内部继续运行随机、延迟、物理或连锁规则。

因此，数字乐器的性格不只来自“有什么按钮”，更来自按钮与系统之间怎样被 Mapping。

Hunt、Wanderley 与 Paradis 在 NIME 2002 的研究中强调，电子乐器不能只被理解成“控制界面 + 声音发生器”，中间的 parameter mapping 本身会定义乐器的核心特征。

研究参考：
- NIME 2002 / The Importance of Parameter Mapping in Electronic Instrument Design：https://nime.org/proc/nime2002_hunt/

公众推文不必展开论文，但可以把结论压缩成一句：

> **我们不是在教你增加更多按钮，而是在练习如何让一个动作产生值得演奏的结果。**

## 7.1 yiyisogreen｜控制信号怎样同时进入声音与视觉

在 yiyisogreen 的部分 Audio Visual 实践中，控制器信号并不是只负责播放视频或调一个音量，而是被同时用于声音与视觉系统。例如《Wet Dream》（2023）的控制信号会同时参与声音采样的切割 / 速度变化与视觉场景操作。

这一类实践与本工作坊的“同源控制”非常接近：重要的不是效果数量，而是同一个 Gesture 如何被分配到多个结果，以及这些结果怎样形成可演奏的关系。

# 8｜为什么是网页？

网页在这里并不是因为“网页最先进”，而是因为它足够轻：

- 不需要先学习一套庞大的专业软件界面；
- 键盘、鼠标、触摸、音频和视觉都可以进入同一个运行环境；
- 可以快速修改、全屏运行和分享；
- 一个完成的原型可以继续被发布成 URL，也可以进一步迁移到 MIDI、游戏引擎、现场软件或更复杂的硬件系统。

因此，网页更像一张公共工作台：让初学者先理解系统，再决定未来要进入哪一种专业工具。

这也对应 Patatap 与 touch:waves 给我们的启发：一个浏览器界面只要建立了清楚的输入、反馈和 Mapping，就已经有可能成为一件可玩的数字乐器。

# 9｜AI 在这里做什么？

AI 在本次工作坊中主要承担：

- 帮助参与者快速建立网页骨架；
- 修改代码与参数；
- 解释报错；
- 把个人声音、图片与交互关系接入 Starter Kit；
- 快速生成不同实现方案供人比较。

但课程不会把 Prompt 或 AI 模型本身当成最终技能。

创作者仍然需要决定：

- 什么是输入；
- 什么应该被 Mapping；
- 什么结果值得留下；
- 作品什么时候该安静；
- 怎样让别人第一次就能玩；
- 什么东西在现场真正成立。

基础循环是：

**人决定 → AI 执行 → 人运行 → 人判断 → 再修改。**

# 10｜参与者最终会得到什么？

三小时以后，每位参与者至少拥有：

- 一个可以运行的网页视听原型；
- 一个明确的 Input；
- 至少一组 Sound + Visual Mapping；
- 一个 State / 变化规则；
- 一次他人试玩；
- 一个 V2 或明确的下一版计划；
- 一次 30–60 秒快速 Showcase。

成果不要求长得一样。

它可能是一件：

- 网页音画乐器；
- 生成视觉系统；
- 声音触发的互动作品；
- 键盘 / 鼠标控制的 Live Visual 工具；
- 可以继续发展成 MIDI / Game Engine / Live Set 的原型。

最重要的是：参与者离开时不是“听过几个软件名”，而是已经有一个可以继续修改的系统。

# 15｜编辑红线 / 不建议直接写进推文的内容

以下内容来自口播稿或旧整理，但在正式 MANA 推文中建议删除或修正：

1. **不要把“音画同源”写成已经有统一定义的正式艺术史流派。** 这是本工作坊用于组织 Visual Music、Audiovisual Instrument、Shared-source Mapping 等方法的工作概念。
2. **不要写 Golan Levin 在 MIT 完成“博士论文《Audiovisual Performances》”或“视听四大名著”。** 对外使用 AVES / *Painterly Interfaces for Audiovisual Performance* 即可。
3. **不要写 Ryoji Ikeda《formula》使用硬盘报错、DNA、CERN 粒子数据。** 这混合了多个项目；“纯数据、硬盘错误”更准确对应 datamatics。
4. **Ei Wada / ELECTRONICOS FANTASTICOS! 的公开项目起点用 2015。** 不要把日本数字电视切换的背景故事直接写成项目成立年份。
5. **Autechre 关灯、Kraftwerk 访谈等故事可以留作课堂口述，不建议成为招生推文的核心论据。** 它们会让开头迅速变成长篇电子音乐史，而且需要额外逐条核源。
6. **不要用“弱智视觉映射”“光污染”“强暴观众注意力”等口播表达进入公开推文。** 可以改成“视觉与声音结构脱节”“视觉成为装饰层”。
7. **不要再写 Robot Kids。** 当前已验证合作记录是 RÖ / Robakidze 与 SRE / UFO Terminal Realtime Liveset；最终对外署名按本人确认版本统一。
8. **不要声称 SRE 使用 Processing + AI，除非补充对应的一手项目记录。** 当前 GitHub canonical record 支持“实时视觉、高帧率、现场状态与信号语法”，但没有支持该具体技术组合。

# 16｜最终一句话

**这不是一堂教人把声音接到视觉效果上的软件课，而是一场关于“怎样设计一件数字乐器”的三小时实验：从一个最简单的输入开始，让声音、图像、规则和人的操作进入同一个可以被演奏的系统。**
