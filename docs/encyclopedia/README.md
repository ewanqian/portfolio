# Ewan Qian 个人百科维护规则

> 状态：内部工作底稿 / source-of-truth layer  
> 用途：为 Portfolio、CV、申请材料、项目页、公开简介与长期档案提供统一事实来源。

## 1. 这层文档解决什么

当前资料已经分布在个人网站、VIRTURA 文档、项目页、工作坊 README、研究稿、PDF、视频与历史提交中。问题不是资料不足，而是同一事实可能出现多个版本：日期、角色、奖项名称、项目版本、协作者署名和“已发生 / 正在进行 / 准备中”容易在多轮改写中漂移。

个人百科不直接替代公开简介。它首先负责：

1. 记录可核验事实；
2. 给每条事实标记状态；
3. 关联证据；
4. 记录冲突与待核验项；
5. 再由公开页面按需要提取。

原则：**Bio 是输出，不是事实源。**

---

## 2. 推荐的信息流

```text
新资料 / 新记忆 / 新项目
        ↓
Claims Ledger 事实账本
        ↓
Evidence / 来源核验
        ↓
状态确认
        ↓
项目页 / Timeline / Profile / CV / Proposal
        ↓
公开发布
```

任何新成就、合作、奖项、入选、投稿、演出或教学记录，优先进入事实账本，而不是直接改首页简介。

---

## 3. 状态词表

只使用明确状态，不用模糊宣传词替代事实。

- `verified-public`：已核验，可公开。
- `verified-internal`：已核验，但暂不主动公开。
- `ongoing`：已发生且仍持续发展。
- `preparing`：正在准备，尚不能写成已提交或已发生。
- `submitted`：已有提交凭证，但尚未入选。
- `selected`：已有正式入选 / 录取 / 邀请依据。
- `presented`：已经公开呈现或演出。
- `unverified`：来自记忆、旧文案或二手记录，尚需原始依据。
- `deprecated`：旧表述，不再继续使用，但保留历史。

严禁状态跃迁，例如：

`preparing → selected`

中间没有提交与入选证据时，不得这样写。

## 5. 证据优先级

从高到低：

1. 主办方 / 学校 / 节展 / 合作方正式页面、证书、邮件或提交回执；
2. 当时形成的项目文件、合同、节目单、展签、现场记录；
3. Git 仓库中的同期项目文档、视频与版本记录；
4. 后来整理的 Portfolio / VIRTURA PDF；
5. 对话记忆、口述与后续回忆；
6. 推断。

第 5 层可以进入待核验区；第 6 层不能作为公开事实。

## 6. 合作项目的署名规则

合作关系必须按 **项目 / 版本** 记录，不建立模糊的“长期共同作者”推断。

例如徐昊合作线应拆成：

- TIMER / 控时者：具体版本、日期、地点、Ewan 角色、徐昊角色、其他团队成员、证据；
- Drop Flow / 滴流：每个版本分别记录；
- 后续项目：重新建条目，不自动继承旧项目署名。

如果同一系列不同版本人员变化，必须保留版本差异。

---

## 7. 身份边界

本百科只维护 **钱誉文 / Ewan Qian** 的个人与职业档案。

不得把其他账号使用者、协作者或历史文件作者的教育、申请、作品、研究方向、教学经历或个人身份并入 Ewan。

特别规则：任何历史材料中出现其他作者时，只能在具体项目 credit 中按证据保留其协作角色；不得由此推导为 Ewan 的个人经历。

---

## 8. 公开写作边界

### 可以直接进入公开简介

- 身份与教育中已经核验的基础信息；
- 已公开呈现的代表项目；
- 已核验的奖项 / 节展 / 展览；
- 明确的项目角色；
- 当前已发生并持续中的实践方向。

### 不直接进入公开简介

- 仅处于准备阶段的申请；
- 尚无正式来源的奖项名称；
- 未确认的合作角色；
- 研究设想；
- 未来版本；
- 未公开客户信息。

这些可以保存在百科账本里，但必须带状态。

## 10. 维护节奏

建议在以下节点做一次百科更新：

- 每次公开展演 / 工作坊结束；
- 每次投稿 / 申请状态变化；
- 每次 Portfolio 大改前；
- 每次 CV / 学校 / 驻留申请前；
- 每月至少一次快速审计。

每次修改优先回答：

1. 新增了什么事实？
2. 证据在哪里？
3. 状态是什么？
4. 哪些公开页面需要同步？
5. 是否与旧版本冲突？

这样 Git 历史本身就成为个人实践演化记录的一部分。
