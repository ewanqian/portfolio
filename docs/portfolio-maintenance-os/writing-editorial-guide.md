# Writing / Editorial Guide
## 个人网站写作、研究笔记与工作坊 Reader 的发布标准

**版本：2026-11-04 · 适用范围：** `/writing`、公开研究短文、演出现场笔记、工作坊教材。  
**示范页面：** [BPM System 2026](../../docs/journal/reactor-bpm-system-2026.md)  
**教材参照：** [Scene Forge — Reader 0.2](../../workshops/minimal-input-lab/reader-02-scene-forge-textbook-v0.2.md)

这是一份编辑和发布工作准则，不是要求所有文章套用同一种形式。目的在于让个人网站的 Writing 保持可读、可信、能够复用，并能明确区分已经完成的出版内容与仍在发展的研究。

## 一、什么可以进入 Published Writing

一篇公开文章应同时满足：

1. **一个具体问题。** 文章开头可以用两到四段话说明：为何要写、所面对的现场或研究问题是什么、读者读完能够理解什么。
2. **一条清晰主线。** 按问题、工作方法、观察／案例、结论展开，章节尽量避免纯术语或“系统很重要”式空泛标题。
3. **可以核对的素材。** 有原始场景、操作截图、项目文献、工具官方资料、实验记录或可复现步骤；引用以可追溯的一手资料为优先。
4. **经验与资料相互照亮。** 区分现场亲历、教学练习、软件规格、国际案例与后续思考；不把别人的实现写成作者已经完成的系统。
5. **词汇能被初学者理解。** 首次出现专业术语时写出它在实际项目中负责什么；当内容有表格或图解，必须比长段文字更容易获取信息。
6. **独立阅读成立。** 不依赖和作者私聊、工作坊前情或仓库 Issue 才能知道本文在讲什么。

**禁止以 Published 标记纯标题、摘要、提纲或尚未写成的栏目占位项。** 有主题不等于有文章。

## 二、区分四类内容

| 类型 | 适用材料 | 网站位置 |
|---|---|---|
| Field Essay / 实践研究 | 有完整问题、现场经验、可核验案例和结论的文章 | Selected Writing / Published |
| Workshop Reader / 教材 | 教学背景、章节解释、示例、练习、验收、参考来源 | Selected Writing 或 Published |
| Research Proposal / 提案 | 已明确研究问题和计划，但没有达到完整论证或系统验证 | Research in progress |
| Editorial Backlog / 内部目录 | 只有标题、摘要、选题、待核验材料 | 保留源文件，不进公开列表 |

**不是“越短越好”。** BPM System 是单篇文章，主线应紧凑；Scene Forge 是教材，允许更长的章节、示例和附录。两者都要减少读者无意义的跳转和扫描成本。

## 三、内容结构

### 现场实践短文的默认结构
1. **标题与简介：** 直接标明问题或方法，副标题说明具体现场案例。
2. **前言：** 从真实场景出发，而不是先定义十个抽象术语。
3. **核心论点：** 用一张可读的系统图或三个操作动作说明。
4. **怎么做：** 从最低可行配置开始，鼠标 / MIDI / OSC 等按门槛展开。
5. **比较与历史：** 只选择与作者技术问题确实有关的同代实践，说明谁做了什么、技术怎样工作、有什么值得借鉴。
6. **现场与跨部门协作：** 作者自己的观察，与声音、灯光、舞美、观看条件的关系。
7. **结论与延伸：** 回到开篇的问题。较长教程、SOP、排练表、排错放附录。

### 教材的默认结构
- 导论与学习目标；最小必需概念；一步步练习；案例与版本比较；验收方法；术语和参考资料。
- 允许表格、时间轴、Stage Plot、Cue Sheet。图必须可显示；代码和表格不应被渲染成破碎的纯文本。
- 正文优先回答“为什么”；步骤里再回答“如何做”。

## 四、图文排版

- 优先使用作者现场摄影和实际操作截帧；图片不必占满整屏。正文在左，右侧补充图、时间线与小型示意；窄屏时保持阅读顺序。
- 动态控件只在读者实际可以操作、且能直接解释核心观点时出现，不为了好看而制造无意义交互。
- **图片不能代替文字，也不应把阅读效率降低到不如 Markdown。**
- 一张图只解决一个问题：例如三种时间、三个 Layer 的透明度、信号走向、舞台结构。
- 深入教程、Ableton 训练或繁复接线放可展开附录；默认阅读页不应被完整 SOP 挤满。
- 图片来源和身份应在作品资料中可追溯；网站图注使用正常的专业署名，不展示未整理的编辑对话。

## 五、引用与历史研究

优先顺序：项目团队与艺术家档案 > 工具技术文档 > 展演机构档案 > 可考证的专业采访 > 转述文章。

对比案例最少回答：

- 项目、年份与操作者是谁？
- 哪一种输入、时间、播放方式或操作流程可以被确认？
- 操作者怎样组织工程，与技术团队怎样协作？
- 对本文的方法有什么具体帮助？其边界是什么？

不要为了制造“悠久历史”把一个现代工作流强拉回一百年前；历史坐标的远近要由问题决定。避免笼统写“国际 VJ 都这样做”，除非有可核实的生产案例。

## 六、公开写作禁用语态

正文不得出现：

- 与助手、项目经理、客户的对话式复述；
- “我不是在瞎编”、“暂时无法证明”、“这只是草案”等本可通过编辑、署名或来源管理解决的元叙述；
- “后续会补”、“先随便做个版本”的过程说明，除非它确实是研究问题的一部分；
- 没有内容依据的史诗化标题、无解释的控制论行话和过多英文字母缩写；
- 重复出现的“未来目标”，掩盖已交付的内容不足。

需要说明研究仍在进行时，**只写读者需要知道的真实研究状态**，其余质量审核与素材出处细节放内部审计文档。

## 七、编辑前后验收

发布前核对：

- [ ] 文章有真实、完整的 `articlePath`，文件存在且非仅摘要。
- [ ] 元数据 title/summary/type/status 与正文一致。
- [ ] 提案与 Working Model 不以 Published / Featured 冒充成品。
- [ ] 没有在一个页面重复显示同一篇文章三次。
- [ ] 手机与桌面上标题、正文、表格与图片能正常阅读。
- [ ] 每张图来源明确，图注支持正文而不是抢占正文。
- [ ] 专业术语第一次出现时获得解释。
- [ ] 明确引用到具体项目或技术原始资料。
- [ ] 新用户无需了解作者先前的聊天记录也能理解。
- [ ] 网站完成源码构建、发布构建及部署后再宣布上线。
